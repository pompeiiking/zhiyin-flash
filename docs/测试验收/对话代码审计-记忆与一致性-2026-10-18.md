## P1

### P1-1 资产正文与版本行分两笔事务、用两把不同的锁提交（正文已变而版本未升 / 版本已升而正文缺失）
- 位置：`zhiyin-business/zhiyin_business/services/asset.py:221-241`（`save_report`：先 `_next_version` → `_assets.save_report(saved)` 提交正文 → 再 `save_version()` 提交版本行）；`asset.py:147-177`（`save_version` 用 `asset_version:{user}:{type}` 锁）；`zhiyin-infrastructure/zhiyin_infrastructure/postgres/repository.py:880-897`（`save_report` 用 `report:{user}` 锁提交正文）；`repository.py:768-802`（`save_version` 用另一把锁 + `max(stored.version, floor+1)`）；`repository.py:856-865`（`get_report(None)` **只从正文表**取最新）。
- 触发条件：两次写之间失败/被中断——数据库/连接异常、进程重启、部署重启、SSE 断连取消（见 P2-6），或 `save_version` 抛错。`_persist_stage_output` 会吞掉落库异常（`orchestrator.py:2516-2560`，`except ... return []`），随后仅以“版本行是否 +1”判断成败（`orchestrator.py:1945-1984`）。
- 影响：
  1) 正文已提交、版本行未提交时：`GET /app/report/full-text`（读正文表）**展示新正文**，而 `list_versions`/工作台面板仍是旧版本号 → 版本号与正文错配；
  2) 同一场景下对话回复会落到“这次没有成功生成…已有内容没有被修改”（因为版本行没 +1），**与用户看到的正文相矛盾**——与第二轮 W2 实测“回复说没改、版本却 +1”同一类问题的反向残留（当时修的是“版本已 +1 却说失败”，未覆盖“正文已变、版本未 +1”）；
  3) 历史版本读取会因 P3-1 回退到更早正文，进一步掩盖错配。
- 建议：正文与版本行必须**同一事务、同一把锁**提交（或版本行先写、正文后写且失败可回滚）；或者读侧统一以版本行 + 版本号取正文，不单独信任正文表“最新”；失败分支应探测“正文是否变化”而不只探测版本行。

### P1-2 并发保存报告时版本号与正文可错位/互相覆盖（同一资产三处版本算式、两把锁）
- 位置：`asset.py:397-404`（`_next_version` 按版本行算）、`asset.py:229-230`（正文按该版本号写）、`repository.py:886-896`（正文保存时又按**正文表** floor 重算 `max(stored.version, content_floor+1)`）、`repository.py:777-788`（版本行再按**版本表** floor `max(stored, row_floor+1)`）。`biz_asset_content` 没有 `(user_id, asset_type, version)` 唯一约束（`postgres/schema/business.py:136-149`），而 `biz_asset_version` 有唯一索引（`business.py:133-134`）。
- 触发条件：两个生成请求并发（双标签页同时点“重新生成”、双击/回车+点击各带不同 `client_msg_id`、重试与首次请求并发）。两次请求各自在不同锁下推进，插入顺序可交错。
- 影响：出现“版本行 V5 指向的正文停在 V4（或指向另一次请求的正文）”；因唯一索引，版本行不会重复，但**正文归属会错**：历史版本下拉里点 V5 看到的是别人的/旧的内容；`get_report(version)` 的回退（P3-1）会把错误隐藏成“看起来有内容”。这正是“版本/状态不一致”的硬路径。
- 建议：报告保存全程一把 advisory lock（`report:{user}` 或 `asset:{user}:report` 二者之一贯穿正文+版本行），版本号只由仓储层在同一事务内分配；`biz_asset_content` 加 `(user_id, asset_type, version)` 唯一约束并让重复保存变成冲突重试。

### P1-3 方向方案保存无并发锁，delete+insert 可互相覆盖/产生重复
- 位置：`repository.py:910-924`（`save_direction_plans`：事务内 `_delete_content` + 循环 `_put_content`，**没有 `_lock`**；对比 `save_report:885`、`save_action_plan:960` 均有 advisory lock）；`repository.py:926-942`（`select_direction_plan`：先 `list_direction_plans` 读全量、内存改 selected、再 `save_direction_plans` 覆盖）；`asset.py:243-271`（生成方向同样走该覆盖式保存）。
- 触发条件：用户点“选它/换一套”与对话正在生成方向方案并发；或两个标签页同时选择/生成。
- 影响：两种写的 delete+insert 事务交错 → 最终内容可能是“选择前的旧方案 + 新选择的补丁”混合、两套方案的 selected 全为 false、或 `list_direction_plans` 返回重复方案（内容表无唯一约束）；同时 `save_version()` 在另一个事务里给这次写配版本行 → 版本行描述与正文内容不一致。选方向是有副作用的用户动作（记 `decision_select/reselect` 行为日志），被覆盖后页面与行为日志也会互相矛盾。
- 建议：`save_direction_plans` 加 `_lock(f"direction_plan:{user}")`，`select_direction_plan` 在同一锁事务内 read-modify-write；内容表加唯一约束（同 P1-2）。

## P2

### P2-1 幂等重放按 client_msg_id 查询不校验会话，可跨会话返回回复（并可能误吞新消息）
- 位置：`orchestrator.py:973-1003`（`_replay_reply` 在落用户轮之前先查；定义在 `orchestrator.py:2248-2270`）、`memory.py:125-130`、`repository.py:540-573`（`find_reply_by_client_msg_id` 只过滤 `user_id + client_msg_id + role='agent'`，**无 task_id**）、`migrations.py:40-46`（索引 `(user_id, client_msg_id)` 非唯一）。
- 触发条件：同一 `client_msg_id` 被发到另一个会话/task_id。前端正常发送用 `crypto.randomUUID()`（`ConversationView.vue:615`），但“失败重试”会复用旧 id；若重试请求携带的 task_id 与会话切换/恢复逻辑不一致（前端重试沿用旧 request 的 task_id，而 UI 已切到另一会话，见 `ConversationView.vue:604-648`），或第三方/脚本重放，即命中。
- 影响：会话 B 的请求返回会话 A 的上一轮回复文本（`TurnResult.task_id` 仍是 B），UI 会把 A 的内容画进 B；同时该消息在 B 不再产生真实回答与落库 → “消息被吞/答非所问”，且用户无法察觉这是跨会话内容。
- 建议：查询键加 `task_id`（`find_reply_by_client_msg_id(user_id, task_id, client_msg_id)`），或在 `_replay_reply` 校验 `reply.task_id == request.task_id`，不匹配则按新消息处理；索引改为 `(user_id, task_id, client_msg_id)`。

### P2-2 行动计划“读-改-写”竞态：锁外读取旧计划继承完成态，并发完成任务会被覆盖回未完成
- 位置：`asset.py:273-309`（`save_action_plan`：`previous = get_action_plan()` → `_inherit_task_state(previous, plan)` → `_assets.save_action_plan(merged)`）；`repository.py:955-963`（保存时才加锁并**整体覆盖**）；`repository.py:965-993`（完成任务走 `update_action_plan`，同一把锁 read-modify-write）。
- 触发条件：用户点“完成”与对话重新生成/校准计划并发（两标签页、或回复生成期间点今日行动）。
- 影响：`save_action_plan` 用读取时的旧 `previous` 计算继承态，随后覆盖写入 → 期间刚被标记完成的任务回到 pending/未完成（完成记录、今日行动 1/N 计数一起回退）。这是“重复写/竞态”的典型，且用户可见（“我刚才明明勾了”）。
- 建议：把 `get_action_plan` + 合并 + 保存收进同一事务/同一 advisory lock（仓储层提供 `save_action_plan(merge=callable)`，与 `update_action_plan` 一致）；或在计划行上加版本号做乐观并发，冲突时重读重算。

### P2-3 会话摘要 upsert 是“读-改-写”且无锁、无长度上限
- 位置：`memory.py:71-92`（`upsert`：先 `get`，`summary = existing.summary + delta`，再 `upsert` 全量 payload）；`repository.py:468-487`（`PostgresConversationMemoryRepository.upsert` 用 `ON CONFLICT ... DO UPDATE payload = EXCLUDED.payload`，无锁、无追加语义）；`orchestrator.py:2402-2465`（每轮 `_remember_turn` 追加“他：60 字 / 主理：120 字”，`await self._memories.upsert` 在 2425 行）。
- 触发条件：同一 (user, task) 并发两轮（双发、重试与首次并发）。
- 影响：后写者用旧 summary 覆盖 → 丢一条增量（会话续接丢上下文）；summary 随轮数线性增长、无截断/摘要再压缩，每轮随黑板进 prompt（见 P2-4），长会话 token 膨胀、模型把旧结论当当前（第三轮实测 30 轮摘要遗漏细节与此一致）。
- 建议：`upsert` 改为 SQL 原子追加（`payload = jsonb_set(... summary = summary || $delta)`）或加 `mem:{user}:{task}` advisory lock；summary 设长度预算并滚动压缩（保留最近 N 轮 + 关键事实清单）。

### P2-4 对话每轮把“全量黑板”dump 进 prompt，其中包含该用户**所有会话**的摘要（跨会话注入）
- 位置：`orchestrator.py:724-740`（`read_blackboard`：`memories = await self._memories.list_by_user(user_id)`——**按用户全量**，非当前会话，736 行）；`orchestrator.py:1669`/`1809`（`blackboard=blackboard.model_dump(mode="json")` 交给引擎）；`zhiyin-orchestration/zhiyin_orchestration/impl/_shared.py:68-120`（`_render_prompt`：无 `context_text` 时把整份黑板书 `【共享状态】` JSON 原样拼进 prompt；对话链路没有 `context_text`）。
- 触发条件：每轮对话；会话越多/摘要越长越明显。
- 影响：模型能看到并可能复述**其他会话**的内容（同账号内跨会话串台、隐私边界扩散），旧会话的结论会被当成当前依据；prompt 体积随会话数增长（与 P2-3 叠加）。第二轮/第三轮实跑里“答非所问/把别的主题带进来”的偶发表现与此路径一致（不排除模型自身波动）。
- 建议：对话链路只注入**当前会话**的 memory（task_id 过滤）+ 必要跨会话事实清单（由 profile/资产提供）；黑板书渲染显式白名单字段，避免整份 dump；长摘要滚动压缩。

### P2-5 会话改名/删除不失效 workspace 读缓存，且不清理用户状态里的会话快照
- 位置：`application.py:340-353`（`rename_session` / `delete_session` 仅调 `workspace.*`，**没有 `_invalidate("session_changed")`/`_invalidate_user`**）；缓存策略里 workspace 明确按 `session_changed` 失效（`data/registry/policy_params.json` cache.workspace.invalidate_on）；`workspace.py:267-292`（list/rename/delete 只改会话仓储与 memory）；`student.py:522-533`（`store_session_snapshot` 写 `snapshot_messages/…`、`session_snapshots[task_id]`、`conversation_reply_snapshots[task_id][client_msg_id]`，`delete_session` 无清理）。
- 触发条件：删除/改名后 20 秒内读工作台（缓存 TTL）；或删除后长期观察用户状态。
- 影响：工作台在 TTL 内仍包含被删会话贡献的 `memories`/`current_stage`/面板，看起来“删了还在”；被删会话的回复快照与消息 id 列表**永久留在 `biz_student_state`**（孤儿数据、含对话原文摘要级内容，删除语义不彻底）。
- 建议：rename/delete 后调用 `_invalidate_user(user_id, "session_changed")`；删除会话时同步清理 `student_state` 中该 task 的 snapshots（`state.update` 里 pop）；并发删除与在途消息的竞态（见下）用“删除标记”或事务内校验处理。

### P2-6 SSE 客户端断开即取消服务端生成，可能出现“资产已落库、对话无主理轮/摘要”，重发再生成一版
- 位置：`conversation_controller.py:110-144`（`worker = create_task(run())`，生成器 `finally: worker.cancel()`，139 行）；`orchestrator.py:2516-2560`（资产落库在 `send_message` 内）；`orchestrator.py:2402-2465`（摘要与逐轮原文在回包阶段写）。
- 触发条件：用户点“停止”、关页/切会话导致 SSE 断开、网络中断；取消发生在 `_persist_stage_output` 与 `_remember_turn` 之间（存在窗口）。
- 影响：报告/计划版本已 +1、但会话里没有主理回复与摘要（刷新后“问了一句，没有回答，报告却变了”）；用户按“重试”重发同一 `client_msg_id` 时 `find_reply` 找不到主理轮 → 重新生成 → **多一版内容相同的新版本**（可能再次触发 P1-2 的并发问题），并产生额外模型费用；若取消发生在正文提交与版本行提交之间 → P1-1。
- 建议：生成与落库放在**不可取消**的 shield/后台任务里（客户端断开只停止推流，不取消业务事务）；对“已落库但无主理轮”的 turn 提供补偿（重发时先查资产是否已生成，直接补回复而不重复生成）。

## P3

### P3-1 `get_report(version)` 缺正文时回退“不晚于该版本的最新正文”
- 位置：`repository.py:866-878`。版本行存在但正文缺失（并发/中断/历史脏数据）时返回旧正文；`application.py:532-557` 又把结果按 `v2:{version}` 缓存 900s。
- 影响：历史版本“第 N 版”显示的是第 M(<N) 版正文且被缓存 15 分钟；用户核对历史/导出时拿到错内容。与 P1-1/P1-2 叠加时是主要放大路径。
- 建议：回退时显式标注“本版正文缺失，显示的是上一版（Vx）”，或不要缓存回退结果；根本修复在 P1-1/P1-2。

### P3-2 用户轮去重只看最近 5 条
- 位置：`orchestrator.py:2379-2401`（`_user_turn_saved` 取 `limit=5`，按 `client_msg_id+text` 或纯文本比对）。
- 触发：重试请求到达时，期间已有 >5 条轮次写入（并发/长生成）；或两条完全相同的无 id 消息。
- 影响：同一条用户消息可能被记两次（会话历史出现重复气泡）；或“连发两句一样的话”在无 id 时被误吞。建议用 `(user_id, task_id, client_msg_id)` 唯一约束做幂等，不再依赖窗口扫描。

### P3-3 会话列表 N+1 与逐会话 200 条扫描
- 位置：`application.py:300-338`（每个会话各查一次 `list_turns(limit=200)` 只为取 `message_count`/最后一句）。
- 影响：会话多时历史面板变慢（N 次 DB 往返），并让 `/app/sessions` 成为重读接口；建议会话表带 `message_count/last_message_at` 或一次 SQL 聚合。

### P3-4 进程内字典无淘汰 + 材料 id 数量无上限
- 位置：`function.py:83-95`（`_intel_cache`、`_last_intel_announce` 按 user 存，无全局淘汰，仅 TTL/显式 drop）；`application.py:478-496`（`_load_materials` 对 `material_ids` 逐个读对象存储，未限制数量/总字数）。
- 影响：长时间运行/多用户下内存随用户数线性增长；恶意或异常请求可一次带大量 material_id 触发多次对象存储读（放大延迟与带宽）。建议：字典设容量上限/LRU，material_ids 限制条数并复用本请求已校验的引用。

### P3-5 画像更正级联的失效顺序（先清缓存、后标版本）
- 位置：`application.py:984-1006`（先 `_invalidate_user("profile_field_updated")`，再 `propagate()` 标记 `needs_recompute`）；`asset.py:132-135` 明确 propagate 不发 `asset_version_changed`、不清缓存。
- 触发：两个并发的“读工作台/报告版本”请求恰好落在两者之间。
- 影响：该用户的 workspace 读缓存可能把**未标记**的工作台视图缓存 20 秒（随后才看到“待核对”）；概率低、窗口毫秒级，但属于可修的时序问题。建议先标记再失效（或同一事件里完成）。
