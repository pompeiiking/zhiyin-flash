## 二、P2 明细

### A-1（P2）停止/生成中离开页面后，“中断”判定错误；pending 标记残留

**代码事实**
- 生成开始时 `markChatPending(sessionId)` 写入 `zhiyin-chat-pending:<id>='1'`；`stop()` 把它改成 `'stopped'`（`ConversationView.vue:288-289,596`）。
- `syncInterruptedNotice()` 一旦检测到 `hasChatStopped`，立即 `clearChatPending()` 并只把“主动停止”写入内存 `requestError`（`:307-313`）——**标记被消费掉，没有持久化**。
- 路由离开/组件卸载时 `onUnmounted` 先 `serial++` 再 `controller.abort()`（`:780`）；而 `send()` 的 catch/finally 都以 `run === serial` 为前提（`:643-664`），serial 已被改，**finally 中 `clearChatPending` 被跳过**。若此时是普通生成中切页，`zhiyin-chat-pending:<id>='1'` 会留在 sessionStorage；只有再次进入该会话时 `syncInterruptedNotice` 才会清理（`:329`）。
- 刷新恢复时 `openSession` 只按“最后一条消息角色”决定 guide 归属（`system-data.ts:27-29`）；随后 `syncInterruptedNotice` 在无 stopped 标记时把“最后一条是 user”直接判定为中断（`:321-328`），并渲染“刷新或切换页面导致/重新发送”（模板 `:899-905`）。
- 退出登录只清失败缓存（`clearAllFailures`，`:176-185`、`auth.ts:101` 派发 `zhiyin:session-cleared`），**不清 `zhiyin-chat-pending:*`**；`clearSystemData` 也不清（`system-data.ts:14-16`）。

**触发条件**
1. 生成中点「停止接收」→ 立刻刷新：`stopped` 标记已在内存态被消费，刷新后只剩“最后一条是 user”，被误判为刷新中断（R3 已复现：`r3-15-stop-reload.png`、`r3-03-delete-stop-error.json` 中 `afterStopReload.interrupted=true`）。
2. 生成中切到其他页面（组件卸载）→ 标记残留；之后重新打开/重新登录该会话，同样被当作“刷新中断”（R2 复现过其它会话残留：`r2-11-old-session.json` 中 `zhiyin-chat-pending:task-3abf…=1`）。
3. 多标签页：A 标签页正在生成，B 标签页打开同一会话——B 无 sessionStorage 标记，看到“最后一条是 user”即误报中断并给重发入口。

**影响**：主动停止被说成系统故障/刷新导致；点「重新发送这个问题」会再次发送已经存在的提问（见 A-2），造成重复消息；多端用户会被引导重复提问。

**建议**
- 停止状态持久化：用不立即删除的标记（如 `localStorage` 键含 session+时间戳，或后端 turn 状态字段），只在“成功回复/用户显式丢弃/下一轮正常发送”后清理；
- 恢复会话时若存在 stopped 标记，展示“上一轮是你主动停止的，可继续补充或重新提问”，不出现“刷新中断”和重发按钮；
- `onUnmounted` 与 `send()` 的清理不要依赖被递增的 serial（分离“视图存活”与“请求序号”）；`clearSystemData`/登出时顺带清理 pending/stopped 键；
- 判断“中断”不只看最后角色，还要结合服务端是否有进行中 turn 或本地 in-flight 标记。

### A-2（P2）中断后「重新发送这个问题」重复用户消息 + 丢失原材料

**代码事实**
- `retryInterrupted()` 直接 `send(false, { text: item.text })`（`ConversationView.vue:331-336`）。
- `send(false, …)` 走普通新消息分支：生成**新的** `client_msg_id` 并追加一条用户 turn（`:597-608,617`）；只有 `retry === true` 分支才做“已有同文本用户消息”去重（`:632`）。
- 原提问在服务端/界面上已存在（中断判定基于“最后一条是 user”），因此重发会在上方保留旧提问的同时再插入一条相同提问。
- 材料：`retryInterrupted` 只传 `text`，`outgoingMaterials` 在非 retry、非 choice 分支取当前 `attached`（通常为空）（`:603`），原 `turn.materials` 没有被复用。

**触发条件**：刷新/切页中断（或 A-1 的误判）后点击「重新发送这个问题」；带材料的那条提问中断后重试尤其明显。

**影响**：同一问题出现两次用户气泡（消息重复）；原消息材料丢失，模型上下文缺材料；若服务端按 client_msg_id 去重则新 id 不会被识别，可能重复记录/重复计费式生成。

**建议**
- 中断重发应复用原请求：从最后一条 user turn 恢复 `client_msg_id`/`material_ids`（需要后端 turns 返回 client_msg_id 或前端在发送时把请求写入 localStorage 与 turn 关联）；
- 或改为“重新生成”语义（原提问不重复显示，仅重新请求回答）；
- 无原请求信息时把按钮改为「继续输入」/「重新提问」，不做隐式重发。

### A-3（P2）SSE 超时/断流被呈现为“已停止”，且不落失败记录

**代码事实**
- `streamBackend` 设置首帧 20s、帧间 60s、总时长 180s 三个定时器（`backend-stream.ts:21-22,56`），任一触发会 abort 内部 controller。
- catch 对 abort 统一映射：`controller.signal.aborted ? '生成已停止，可保留输入后重试。' : '生成中途断开了…'`（`:66-68`）——**超时与用户停止无法区分**。
- `ConversationView.send` 的 catch 以 `stopped.value` 判断分支（`:643-659`）：超时不会置 `stopped`，错误文案却来自上述 BackendError，用户看到“生成已停止”；
- 只有非停止分支调用 `rememberFailure(...)`（`:661`），停止分支不落失败记录；超时被误归“停止”时同样没有失败卡，刷新后只能看到可能误判的 interrupted（A-1），没有“重试上一条失败消息”的持久入口。

**触发条件**：弱网/服务排队导致首帧 >20s、帧间隔 >60s、总时长 >180s；用户并未点停止。

**影响**：用户以为自己误触停止；真实失败没有可持久恢复的失败记录（刷新后无法重试原请求）；与“停止不是失败”的语义相悖。

**建议**
- 用 `AbortController` 的 reason 或独立标志区分 `user-stop / idle-timeout / total-timeout`，文案分别为“已停止”“生成超时，可重新尝试”；
- 超时也走 `rememberFailure`，保证刷新后能重试原请求（含 client_msg_id）；
- 如需更强容错，可评估 SSE Last-Event-ID/断点续传（当前无重连，`backend-stream.ts:54-65`）。

## 三、P3 明细

### B-1（P3）`loadShell` 无去重 + 每次发送触发；壳层错误跨页串场
- `ConversationView.vue:642`：每次发送成功 `void loadShell()`；`system-data.ts:54-76` 一次发 5 个请求（sessions/action/notes/workspace/notifications），无并发序号/去重；`systemData.error` 只取第一个 rejected（`:73-74`）。
- `App.vue:140` 全局错误条明确排除 chat（`route.name !== 'chat'`），但其它页面会显示；因此“聊天成功 → loadShell 某接口失败 → 用户去报告/今日页看到‘部分资料加载失败’”属于错误串场。
- 并发 `loadShell` 后写覆盖：sessions、notices（`refreshNotifications` 会重置 notice 队列与下标）、`systemData.error` 均可能被后到响应覆盖；连续发消息时更明显。
- 建议：loadShell 增加 in-flight 去重与 generation 序号；发送成功只刷新必要域（sessions/snapshot），错误按来源归属或在对话页也提示壳层失败。

### B-2（P3）`openSession` 在 `chatBusy` 时静默返回
- `system-data.ts:18-19`：`if (demo.state.chatBusy) return`（无错误、无提示）；`ConversationView.vue:496 resume()` 在 `await openSession(id)` 后继续 clearing 状态、关历史面板、`bottom()`，无法区分“切换成功”与“被忽略”。
- 当前 UI 有 `thinking` 前置守卫（`:496`），触发面小；但任何新增入口（如侧栏/手机历史）复用 `openSession` 时会静默失效。
- 建议：返回 boolean 或抛“正在生成，稍后可切换”，由调用方给出反馈。

### B-3（P3）空会话错误双 `role=alert`
- `ConversationView.vue:907`：`v-if="requestError && !showFailedSend"`（对话区）；
- `:929`：`v-if="requestError && !turns.length && !pending && !showFailedSend"`（输入区上方）。
- 两者可在“turns 为空 + 已有 currentSessionId + requestError（如 resume/openSession 失败）”时同时渲染，同一文案两条 alert（读屏重复播报，视觉重复）。
- 建议：后者仅在对话区未渲染时显示（加互斥条件）或合并为同一节点。

### B-4（P3）会话列表刷新与重命名/删除竞态
- `refreshSessionList`（`:364-376`，由 `watch(historyOpen)` `:486` 与 focus/visibility `:377-381` 触发）没有序号/取消；`applySessionListResult`（`:355-363`）直接覆盖 `backendDemo.setSessions`。
- 触发：打开历史面板触发刷新 → 用户立刻重命名/删除 → 重命名响应先到并把列表更新，随后更早发起的刷新响应到达用旧列表覆盖 → 标题/行“回退”，直到下一次刷新。
- 建议：会话列表请求加 generation，只有最新请求可落地；或操作响应落地后作废在途列表请求。

### B-5（P3）读屏 / 焦点 / 稳定 id
- 消息区 `.consult-messages` 仅有 `:aria-busy="thinking"`（`:857`），无 `role="log"`/`aria-live`；`:909` 的 sr-only 只播报“正在接收回复/回复已到/回复已停止/回复失败”，**正文不可被逐段播报**（读屏用户无法感知新内容，只能手动导航）。
- 删除确认块 `role="alert"`（`:801-806`）无自动聚焦/焦点返回；点击「删除」后该按钮被替换，焦点丢到 body；`askDelete`（`:423-433`）无 focus 管理。重命名编辑器有聚焦（`:394-399`），但取消/保存后未回到行内按钮。
- `interrupted`（`:899-905`）与 failedSend（`:893-896`）用 `role=alert` 包按钮；`pendingConfirm` 用 `role=status` 包按钮（`:914-920`），实时区域含交互控件会被重复播报且语义不当（应 alertdialog/dialog + 明确的 live 文本）。
- turn id 不稳定：`mapMessage` 用 `${session}-${i}`（`system-data.ts:29,45`），发送时用 `${client_msg_id}-user`；`confirmDismissed` 只存内存（`ConversationView.vue:49,268-282`），刷新后 id 全变且 dismiss 记录丢失 → 已答过的“可以/先不要”在特定历史结构下可能重新弹出；`copiedTurn`、`latestHostId` 等 id-keyed 状态同样刷新即失效。
- 建议：消息容器设 `role="log"`（或对新增 host turn 用独立 live 文本）；删除确认聚焦“取消”并返回触发按钮；交互型提示改 dialog 语义；消息 id 用服务端 message id/client_msg_id 稳定化；确认状态持久化或由服务端确认字段驱动。

### B-6（P3）短屏移动端输入区预留不足
- 基础移动样式为 `padding:8px 12px calc(34px + env(safe-area-inset-bottom))`（`conversation.css:197`）；
- 短屏媒体查询 `@media(max-width:767px) and (max-height:700px)` 将 `padding-bottom` 压到 **4px** 且隐藏 disclaimer（`:219-223`）。
- 实测（headless，底栏 fixed）：390×667 输入表单 bottom 591 / 底栏 top 595 → **间距 4px**；320×568 → 间距 6px；发送按钮未被覆盖，但无安全余量，真机键盘/手势条/浏览器工具栏变化时容易压到底栏。
- 建议：以 `--bottom-nav-height` + safe-area 计算（至少 56–60px）保留底部空间，短屏也不要降到 4px；或在短屏把 disclaimer 行改为保留间距。

### B-7（P3）backend-client / stream 细节
- `backend-stream.ts:27,32,64` 的 `ensureSameAccount` 抛出 1004 时**未派发** `zhiyin:unauthorized`（与响应路径 `:36`、`backend-client.ts:74,85` 不一致），账号切换后可能停留在旧视图。
- `backend-client.ts:89-92` 把任何 abort（包括路由卸载/调用方 signal）统一报“等待超时，输入内容已保留”，与 stream 侧文案不一致。
- GET 800ms 缓存（`:38-45,95-110`）与写操作并发：写开始清缓存，但早于写发起、晚于写完成的在途 GET 仍会返回旧快照；调用方若在写后立即读取可能拿到写前数据（跨页数据不同步风险）。
- 建议：1004 统一派发登出事件；abort 区分来源；对“写后读”关键路径强制绕过缓存或等待写完成。

### B-8（P3）发送失败态残留与失败卡隐藏
- `send()` 失败分支不清 `pending`（`:643-663`），模板 `:906` 会继续渲染“回复未完成”的 pending 气泡（带已收到的部分文本），与 requestError 同时存在；刷新后 pending 消失，呈现不一致。
- `showFailedSend`（`:186-190`）用“同文本用户 turn 是否存在”判断是否显示失败卡：用户重复发送同一句话且最新一条失败时，失败卡被隐藏（只剩 requestError 的重试按钮），用户不容易看出是哪条失败。
- 建议：失败时明确 pending 状态（保留/标记失败）并在刷新后一致呈现；失败卡匹配改用 client_msg_id；同文本重复发送时生成不同 turn id 以便区分。

## 四、已检查、未发现问题的点（避免误报）

- 双击发送防重：`send()` 的 `thinking` 守卫 + `stopArmed` 700ms（`ConversationView.vue:598,613-614,934`）——浏览器 R3 实测双击仅 1 条。
- 成功重试去重：`retry === true` 时按 `client_msg_id-user`/文本查重（`:632`），正常失败重试不会重复插入用户消息。
- 停止文案：修复后 `watch(requestError)` 在 `stopped` 时播报“回复已停止，已接收的内容保留。”（`:704-709`），R3 实测正确。
- 并发帧/会话隔离：流式回调用 `run !== serial || currentSessionId !== sessionId` 丢弃旧帧（`:622-629`）。
- 滚动跟随：`use-conversation-scroll.ts` 以 wheel/touch/pointer/arrow 释放 pin，`bottom()` 只在 pinned 时滚动（`:10-27,36-39`），不会强制拉回正在阅读的用户。
- 错误文案技术异常收敛：`friendlyError` 过滤英文/JSON 类异常（`:196-203`），材料错误有中文口径（`:214-237`）。
- 失败记录清理：登出/`zhiyin:session-cleared` 清 `zhiyin-chat-failure:*`（`:176-185`，`auth.ts:101`）；删除会话清该会话失败与草稿（`:443-444`）。
- 账号隔离：请求头/流式帧都有 token 一致性校验（`backend-client.ts:68-85`；`backend-stream.ts:26-28,32,64`）。
- 弹层可访问性：`AnchoredCard` 基于 reka-ui Popover（`aria-expanded/aria-controls/aria-haspopup`、PopoverClose、Escape/焦点归位由库处理，`AnchoredCard.vue:28-60`）；`DetailPopover` 有 Esc 处理与焦点恢复（`DetailPopover.vue:23-41`）。
- 移动端可用性：textarea 16px、发送/停止 44px、移动端隐藏 Enter 提示（`conversation.css:199-200`）；R3 实测 390/320 无横向溢出、输入区与底栏间距 83/85px（正常高度）。
- `withGuide` 防残片：`system-data.ts:27-29` 在最后一条为 user 时不挂上一轮 guide；`syncInterruptedNotice` 另有 phantom 清理（`:315-320`）。
