## 三、已确认缺陷

### D1（P1）空画像门禁按“关键词”触发，换说法即绕过并生成空报告；且回复自相矛盾

- 复现：新账号 `agent-r2-w1-a-mvdrzr77`（coverage=0、fields=[]）→ 发 `先讨论，讨论完再帮我生成报告。`
- 实际：200，`stage=diagnose`，`changed_assets=["report:1"]`；`GET /app/assets/report/versions` → `[{version:1, depends_on_profile_keys:[], needs_recompute:true}]`（生成时画像为空，`needs_recompute` 因后续补兴趣才置 true）；回复文本同时含“报告先不急着出，现在档案里专业、年级、方向都还空着…先聊清楚…”与“**诊断报告已生成**，可以到对应页面查看…”。
- 期望：空画像一律不生成（无论用“资料不足”还是“先讨论再生成”表达）；讨论轮不生成；不得先说不生成又追加“已生成”。
- 代码依据：
  - `zhiyin-business/zhiyin_business/services/orchestrator.py:1171-1185`：`report_basis_missing` 需同时满足“画像无字段”**且**消息命中 `(资料不足|没有资料|信息不足|资料太少|还没填|没什么信息|空白)` 关键词——不含这些词的空画像请求不触发门禁；
  - `orchestrator.py:230-249`：`_explicit_report_request` 对“先说讨论…再帮我生成”因同句存在“帮我+生成”而判定为显式生成；
  - `orchestrator.py:1912-1918`：门禁未触发时走正常生成，成功后统一追加“…已生成，可以到对应页面查看”。
- 建议：门禁改为**只看画像状态**（`_has_report_basis(profile)`）而非消息关键词；讨论/混合意图（“先讨论…再生成”）返回“先讨论，确认后再生成”，不得同一轮写资产；追加“已生成”前确认本轮确实生成且回复未表达“不生成”。

### D2（P2）提醒请求被路由到“更新报告”兜底，回复与提醒无关且无提醒落库

- 复现：空画像账号发 `明早九点提醒我投简历。`
- 实际：200，stage=diagnose，changed=[]；回复：“**这轮先不更新报告，也不把上一版结论当成新依据。**你直接把想核对的那一段报告原文，或岗位要求贴过来…”；guide“这次没接住你的问题…”，`GET /app/notifications`（全量）无提醒记录（仅学职推送）。
- 期望：识别提醒意图，创建提醒/提醒卡（或提示需要日期/事项），不得回报告更新兜底。
- 代码依据：该兜底文案来自 `orchestrator.py:3287-3306`（`_unsafe_diagnose_fallback`），说明该消息被判到 diagnose 且模型产出被安全兜底替换，提醒意图未进入提醒处理分支。
- 建议：意图路由补“提醒/闹钟/到时候”类；兜底文案按用户意图分支给出（提醒不可用时应说明能力限制，而非报告话术）。

### D3（P2）大五/五年制请求同样落到无关兜底，虽未写档案但无年级限制提示

- 复现：空画像账号发 `我是大五五年制，帮我记一下。`
- 实际：200，changed=[]，profile 未写（正确）；但回复与 D2 相同：“这轮先不更新报告…”+“这次没接住你的问题…”，**未出现**“仅支持大一到大四”的年级限制提示（对比“研究生”请求有明确提示）。
- 期望：PRO-005 拒绝写入 + 提示仅支持大一到大四。
- 代码依据：同 `orchestrator.py:3287-3306` 兜底路径；年级限制提示仅在 `orchestrator.py:1929-1938`（研究生/硕士/博士正则）覆盖，未覆盖“大五/五年制”。
- 建议：年级限制正则补“大五/五年级/五年制/其他阶段”；兜底文案不混用报告话术。

### D4（P2）多任务完成只处理第一个序号，第二个任务未完成

- 复现：B 账号已有 11 项计划（第一项已完成）→ 发 `把第一项和第二项都标完成。`
- 实际：92ms，`changed_assets=[]`；`GET /app/plan/action`：`t_1_1.done=true`（原已 true）、**`t_1_2.done=false`**；回复“「打开3个招聘平台…」已经是完成状态了，这次没有重复修改”，完全未处理第二项。
- 期望：ACT-014 多任务/批量完成——两项都标完成并回读。
- 代码依据：`orchestrator.py:271-330` 的序号解析 `re.search(r"第\s*([一二三四五六七八九十\d]+)\s*(?:项|个|件|条)?", message)` 只取**第一个**匹配（312-314），不支持“和/、/以及”多序号。
- 建议：解析全部序号（`findall`）并对每个匹配任务执行 set_done；多任务时逐条回读、任一失败要说明。

### D5（P3）计划“改短”回复声称已改，但计划文本与版本均未变化

- 复现：B 账号发 `计划里第二项太长了，帮我改短一点。`
- 实际：200，stage=review，`changed_assets=[]`，action_plan 版本仍 v2；回复“这一轮**先把它的动作改小**，别的先不动”，但 `/app/plan/action` 中第二项文本与之前完全一致；随后又追加“要查看你已有的行动计划…”（与“已改”矛盾）。
- 期望：要么真实修改（版本+1）并回读，要么明确“只是建议/需要确认”，不得声称已改。
- 建议：把“改短/改写任务”为写意图时走 plan patch 并回读；若仅给建议，回复不得用完成态措辞。

### D6（PARTIAL，口径待确认）技能未写入画像，仅留在对话

- 复现：空画像账号发 `我会 Python 和 Excel，帮我记到技能里。`
- 实际：changed=[]；profile 最终无 skills 字段；回复“这条我先记在对话里。但档案里专业、年级、经历都还空着，**技能没有落脚的地方**…挑一件你用它做过的事说给我听，这条技能才算站得住”。
- 说明：当前画像词表/采集计划无独立 skill 字段（对照 `policies/collection.py` 的字段清单），产品是否要求“技能”必须落库需确认；本轮按 PARTIAL（未落库，理由合理但未写）记录，不判缺陷。
