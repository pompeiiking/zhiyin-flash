# 对话五个角色与顶部状态条检查

日期：2026-10-22。检查分支：个人画像重构，代码起点 43b5cdb。

## 结论

五个角色及其专业提示词在运行数据库中都已启用，各自职责和方法加载代码存在；但不能判定实际出场正常。真实模型采样发现，不点名角色时，规划、复盘和方向取舍任务可能直接由模型回答，既未加载专业指令，也未更新主理与工作重点。顶部条会忠实显示这个没有更新的阶段，因此出现正在做规划却仍显示“了解自己”。

角色加载成功后的正常持久化链路通过专项测试和真实模型验证。失败、主动停止及多角色协作仍有边界问题。

## 五个角色及应当出场的时机

| 内部角色 | 学生端显示名 | 应当参与的情况 | 当前允许的工作重点 |
|---|---|---|---|
| profile_analyst 建档分析师 | 信息采集顾问 | 梳理经历、兴趣、偏好、现实约束，澄清本人事实 | collect 了解自己 |
| career_advisor 职业顾问 | 职业分析顾问 | 分析差异、核对职业要求、比较方向和取舍 | diagnose 梳理判断；decide 比较选择 |
| path_planner 路径规划师 | 行动规划顾问 | 拆分步骤、安排时间、确定完成标准、调整行动计划 | act 安排下一步 |
| companion_coach 陪伴教练 | 行动支持顾问 | 执行受阻、反馈、复盘、调整推进方法 | review 回顾调整 |
| info_scout 信息侦查员 | 就业资讯顾问 | 查询学职平台、知识库等外部事实 | 协助当前主理，不独立改变阶段 |

这里不存在按分钟、按轮数或按固定顺序上场的机制。普通事实答复和闲聊允许不切换；工作重点可随主题前进或返回，并非完成百分比。信息侦查员当前被定义为辅助角色，加载时不会取代主理头像，这一点是现有设计，不是其配置丢失。

## 真实模型采样

从运行数据库只读取得当前五个角色和提示词，使用当前真实模型；业务容器中的用户、会话、资产均为隔离内存数据，没有改动现有学生资料。共八个独立场景，每个场景只采样一次，结果用于复现问题，不代表稳定成功率。

| 场景 | 实际主理／重点 | 是否产生角色加载事件 | 判断 |
|---|---|---|---|
| 通过聊天梳理兴趣，暂不匹配职业 | profile_analyst／collect | 无 | 署名碰巧与默认角色相同，未证实采集专业指令实际加载 |
| 分析软件测试与后端开发的差异 | career_advisor／diagnose | 有 | 正常 |
| Python 文件读取，三天、每天 20 分钟的步骤 | profile_analyst／collect | 无 | 已写出三天计划，主理与重点未切到规划 |
| 上周任务太大，只练一次，讨论执行卡点 | profile_analyst／collect | 无 | 已进行复盘式交流，教练未加载 |
| 查询学职平台软件测试职业介绍 | profile_analyst／collect | 无 | 给出了取数信息，但侦查员专业模块未加载 |
| 比较两种体验并做可撤回的方向取舍 | profile_analyst／collect | 无 | 已形成方案提议，仍未切到职业分析及比较重点 |

| 明确点名陪伴教练后要求复盘 | companion_coach／review | 有 | 正常，加载约在 1.82 秒，首段文字约在 7.02 秒 |

## 已确认问题

### P1：专业任务的角色选择依赖可被省略的工具调用

`dialogue_engine.py` 使用统一主提示词启动模型，专业提示词只有调用 `use_specialist` 后才返回给模型。初始 `presentation.lead` 和 `presentation.stage` 沿用会话值；业务服务只有看到非空 `dialogue_roles` 后才更新阶段。

因此模型即使已经输出规划或复盘内容，也可能没有任何角色切换事件。真实模型采样已复现。仅检查配置齐全或强制调用角色工具的单元测试，会遗漏这一问题。不能用关键词路由来修补。

### P1：临时工作重点在终态没有统一收口

`ConversationView.vue` 的 `currentStage` 优先使用 `liveFocus`。SSE 收到 `role.selected` 就更新它；但成功终态、失败和停止分支没有统一清空，只有下一次发送或切换会话时才重置。

后端在生成无效时保留旧角色和阶段，已有专项测试覆盖这一约束；前端仍可能优先显示本轮未提交的临时阶段。需要在收到权威终态后采用服务端阶段；失败或停止时回到已确认状态，并在需要时刷新执行状态。

### P2：主动停止后半段回复可能署错角色

停止分支使用 `speaker: host.value` 保存已接收文字，`host` 来自上一份会话快照；如果本轮流式过程已经切换主理，`pending.agent` 才是本轮实际身份。停止时却先把 `pending` 清掉，再使用旧身份。因此半段回答可能在停止后更换头像和署名。

### P2：工作重点与探索模式容易混用

点名教练的真实场景中，模型曾调用 `record_exploration(mode='review')`，被工具参数校验拒绝。合法探索模式是 explore、answer、act、paused，review 则是顶部工作重点。这两个概念没有在模型操作中保持足够清楚的边界。该错误没有导致本次角色切换失败，但会消耗工具往返，并影响工作线索记录。

## 代码确认的潜在风险

- `use_specialist` 每加载一个非侦查员角色，就直接替换主理和阶段。协作时“最后加载的角色”自动成为主理，加载辅助能力与选定最终主理没有区分。这是可见实现行为，尚未在本轮真实协作场景中复现误署名。
- 不加载新角色的闲聊会沿用旧阶段。这可以符合“保留当前重点”的设计，但不能把顶部条理解为每句话的准确分类或线性咨询完成进度。

## 正常项与验证边界

- 五个角色、五份角色提示词和主提示词在当前数据库均为 enabled。
- `test_dialogue_specialists.py` 与 `test_conversation_stream_text.py` 合计 18 项测试通过，覆盖不同指令加载、禁用角色、职责不匹配、阶段持久化、生成无效不提交阶段及流式文本。
- 顶部条渲染五个重点，只标记当前项，没有把前面的项自动标成已完成。它的正常数据映射与现有设计一致。
- 当前前端四个标签中的业务页均已回到登录入口，本轮未重新登录，因此没有声称完成登录态浏览器的头像切换、手机布局及停止点击端到端验收。前端边界问题由代码路径与后端测试确认。
- 本轮只检查和记录，没有修改对话业务代码、提示词或数据库配置。

## 建议整改顺序

1. 把本轮主理与工作重点变成 AI 必须明确给出的受约束决策，后端校验；避免仅依靠“可能调用的角色工具”。专业职责需要实际进入该轮上下文。保留语义判断，避免关键词路由，也不要为每轮增加五次模型调用。
2. 分离加载协作者与选定主理，明确谁负责最终回复；侦查员可持续作为事实协助。
3. 统一前端成功、失败、停止的阶段收口；保留本轮实际说话身份，避免停止后错署名。
4. 工具说明明确区分 exploration mode 与 stage/focus，并补充规划、复盘、方向取舍、主题回退、协作和流式中断的真实模型验收。
