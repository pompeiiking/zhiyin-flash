# 个人画像设计实施与检查记录

日期：2026-10-20。依据：[个人画像设计（2026-10-20）](../../产品与架构/个人画像设计-2026-10-20.md)（下称“设计”）。

本文记录**本轮实际改了哪些代码、验证到什么程度、哪些还没实施**。它不是设计通过记录：设计第 11 节的 32 项验收里，只有一部分能在本地自动化中执行；真实模型、真实数据库迁移与正式前端浏览器验收仍未完成。本轮**未推送、未部署**。

## 1. 本轮实施内容

### 1.1 记录结构与语义契约（设计第 2、4 节）

- `zhiyin-kernel/zhiyin_kernel/enums.py`：新增 `ProfileEntryType`（学习背景/兴趣/经历/能力/职业关注/价值取向/现实条件/补充信息）、`ProfileEntryStatus`（有效/已更正/冲突/过期/撤回）、`ProfileVerification`（自述/本人确认/资料记录/已核验/待核对）、`ProfilePurpose`（五种用途）。
- `zhiyin-kernel/zhiyin_kernel/blackboard.py`：`ProfileField` 增加 `entry_type`、`attributes`、`verification`、`status`、`origin_ref`、`valid_from`/`valid_to`/`event_at`、`entry_version`、`superseded_by`。全部有默认值，老数据读出来仍是合法记录；`confidence` 保留为兼容字段。
- `zhiyin-kernel/zhiyin_kernel/profile_taxonomy.py`（新增）：受控词表 —— 字段键 → 内容类别、来源 → 默认核实状态、各类型取值上限与多值条数、类型专属属性（兴趣的正负与情境、职业关注的了解/考虑/已选、能力的证据类型等）、用途 → 可读类别。类别与属性由服务端计算，模型不能自报。
- `zhiyin-business/zhiyin_business/services/profile.py`：`update_field` 统一校验类别、取值形状、属性、核实状态与有效范围；不再用统一 40 字承载所有记录（经历 12000、兴趣最多 8 条、短事实仍 40）；每次写入版本 +1；事件带上类别与核实状态。用户更正标记为 `user_confirmed` 并清掉描述旧值的属性。
- 数据库：`biz_profile_field` 新增上述列（建表语句 + 幂等增量补丁），PostgreSQL/内存仓储同步读写。老库缺列时按默认值读取，类别按词表兜底推导。

### 1.2 取数契约：专业检索独立、兴趣退出职业检索（设计第 8 节、第 10 节第 1 步）

根因（设计第 1 节复现的问题）：学职网关把 `interest`/`industry` 当成职业检索词。加入“把东西真正跑起来的过程”后，职业与案例查询改用了兴趣描述，得到 0 个职业和无关案例。

- `zhiyin-infrastructure/zhiyin_infrastructure/xuezhi/gateway.py`：职业检索词只来自**明确的职业关注**（`target_direction`/`target_job`/`career_interest` 等），普通兴趣、价值取向、现实条件、补充信息一律不进入；专业检索始终独立执行；职业有官方专业映射时优先用映射，没有才按名称检索。
- 返回 `details`：本次检索依据（专业词/职业词）、专业/职业/案例各自条数、职业是官方映射还是名称检索。`DataSourceResult` 增加 `details` 字段。
- `zhiyin-business/zhiyin_business/policies/intel_query.py`：情报主题只从专业（优先）或明确的职业关注推出，不再按字段中文名含“方向”就取兴趣值。
- `zhiyin-business/zhiyin_business/services/function.py`：取数状态按专业/职业/案例分别报数；职业 0 条时明确“这不代表平台没有收录”，空结果不再写成“平台未收录”或整次成功。
- API：`IntelListView` 增加 `counts`/`query`/`occupation_sources`，前端可回看取数依据。

### 1.3 展示与用户控制（设计第 9 节）

- `ProfileFieldView` 下发类别、类别中文名、核实状态与中文名、属性、来源引用、有效范围与版本；OpenAPI 快照与前端类型已重新生成。
- 个人画像页按三种内容组织：**你提供的信息 / 系统基于证据的理解 / 近期补充与变化**；每条显示内容类别与核实状态（本人自述、本人确认、资料记录、已核验、待核对）。
- 页面不再展示“整体可信度”百分比，各条不再显示内部置信度条；改成“有来源支持 / 本人自述 / 待核对”的计数与来源说明。首页资料概览的“资料完整度”改为“已记录资料”，待补充文案改为“可以补充，不影响继续交流”。
- 对话右侧画像摘要与现有导航、其他页面未改。

### 1.4 回归测试

新增 `tests/test_profile_design_2026_10_20.py`（15 项），覆盖：

- 专业只作为学习背景，不自动长成兴趣或职业目标；兴趣多值 + 正负与情境；职业关注保留“了解”状态；各类型长度/条数上限；属性受控；有效范围校验；来源与核实状态分开；冲突/撤回记录退出用途读取。
- 取数：专业＋兴趣时专业检索保留且兴趣不成为检索词；短兴趣词不做模糊职业匹配；只有兴趣时不发起学职检索；明确职业关注才成为职业检索词；官方映射与名称检索分开报告；取数状态分别报数且“职业 0 条”不写成平台未收录。

既有相关测试（数据源、画像更正、对话运行时、字段长度、显示名、表结构迁移、架构守卫等）全部通过。

## 4. 仍未实施的部分与原因

1. **待验证线索（设计 3.2）**：需要独立的线索存储、依据引用、失效与重新分析流程；本轮只保留了会话探索快照，没有把它变成画像旁路的线索记录，也没有前端“否认这条理解”的入口。
2. **统一记忆策略的显式授权（设计 5.2）**：账号/会话/单条拒绝已持久化并在服务端写入前执行，但“只保存这一条”和带来源、可回读的策略记录未实现；“这条不要记录”目前是按键拒绝，不是按内容拒绝。
3. **冲突并存与用户裁定（设计 7）**：有状态字段和版本校验，但没有“两条来源并存、由用户选择”的完整流程与展示。
4. **旧数据迁移（设计 10、P28）**：既有 `interest` / `career_interest` 别名与历史含糊值没有迁移脚本；本轮靠词表运行时推导类别，未改写数据。
5. **真实环境验收**：真实模型多轮采集、PostgreSQL 迁移、真实学职平台、桌面/手机浏览器、部署与回滚都未执行。设计第 12 节列出的正式 schema、容量、保留期限、兼容期限仍未定稿。

## 5. 结论

本轮把设计里“记录结构 + 消费契约”的根因改动落地了：写入侧有类别/核实状态/来源引用/版本，读取侧按用途取词，专业与职业检索分离，兴趣不再冒充职业名称；展示层按三种内容组织并去掉内部置信度展示。设计第 11 节的 32 项验收中，本地自动化可判定的部分已通过，线索、显式授权、冲突裁定、旧数据迁移和真实环境验收仍未完成，不能把本文当作全量验收通过记录。
