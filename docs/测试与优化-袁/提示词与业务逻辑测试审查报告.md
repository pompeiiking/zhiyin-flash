## 3. 整体业务逻辑

### 3.1 对话主链路

```text
用户消息
  → 按 client_msg_id 查重
  → 读取会话、画像、行为、资产和记忆
  → 关键词意图规则 / 实际进度规则选择环节
  → 采集门槛与主理选择
  → 组装最近对话、选项身份、画像键、理论卡和外部事实
  → 按环节契约调用模型、校验结构化产出
  → 采集写画像；诊断/决策/行动写资产
  → 保存逐轮记录与行为、使相关缓存失效
  → 返回回复、证据、可视件、告知和下一步引导
```

实现入口见 [`orchestrator.py`](../../zhiyin-src/template/zhiyin-business/zhiyin_business/services/orchestrator.py)。意图和环节判定主要是**规则**：明确意图优先；未命中时看实际进度；仍无法推进时留在当前环节继续对话。见 [`routing_rules.py`](../../zhiyin-src/template/zhiyin-business/zhiyin_business/policies/routing_rules.py)。

### 3.2 五环节及业务边界

| 环节 | 主理 | 主要产出 | 边界 |
| --- | --- | --- | --- |
| ① 采集 | 建档分析师 | 字段更新、缺口、追问 | 真实字段写画像；不替用户下职业结论 |
| ② 诊断 | 职业顾问 | 报告、差距与依据 | 外部要求需可追溯；不替用户选方向 |
| ③ 决策 | 职业顾问 | 主攻、平行、保底方案 | 用户选定且可撤回，说明各方案代价 |
| ④ 行动 | 路径规划师 | 阶段、任务、节点 | 任务要可执行；拆不动时允许检查方向 |
| ⑤ 复盘 | 陪伴教练 | 归因、进度和最小行动 | 依据实际行为，不把停滞归咎于用户 |

五份结构化契约位于 [`contracts/`](../../zhiyin-src/template/zhiyin-business/zhiyin_business/contracts/)。九项页面生成任务由 [`ai_tasks.py`](../../zhiyin-src/template/zhiyin-business/zhiyin_business/services/ai_tasks.py) 分配角色、提示词和契约；学籍核验与学业导入属于数据链路，回执不由模型编造。

诊断、决策和行动环节可以主动获取外部事实；采集和复盘只读现有缓存。主动提醒根据真实行为、停滞阈值、冷却期及窗口次数触发，投递文案实际来自 `copies.json` 的 `notify.stall.*`。见 [`active_event.py`](../../zhiyin-src/template/zhiyin-business/zhiyin_business/workers/active_event.py)。

## 5. 提示词层级及问题

### 5.1 层级与调用

| 层 | 数量 | 条目与用途 |
| --- | ---: | --- |
| `core` | 1 | `core.system`：共同总纲 |
| `guide` | 1 | `guide.closing`：每轮输入中的对话收尾规范 |
| `role` | 6 | 采集、诊断、决策、行动、复盘及信息侦查员角色 |
| `router` | 1 | `router.clarify`：新会话无法定位时的固定澄清文案 |
| `disclosure` | 7 | 主理交接模板、五个环节原因、结论变化告知 |
| `proactive` | 1 | `flow.proactive`：配置存在，尚未接入实际通知链路 |
| `task` | 9 | 今日简报、维度解读、画像分析、日建议、缺口追问、报告小结、周计划、待办建议、方向匹配 |

26 条均为 enabled，`code` 无重复，**均无独立版本字段**。普通对话组装“总纲 + 环节角色 + 注册表角色描述”，再传入“收尾规范 + 本轮上下文”；产出结构由契约约束。页面任务指定 `prompt_code` 时，该任务提示词占角色位置，同时仍加载总纲和收尾规范。见 [`agno_engine.py`](../../zhiyin-src/template/zhiyin-orchestration/zhiyin_orchestration/impl/agno_engine.py)。

### 5.2 按优先级排列的发现

| 优先级 | 发现与证据 | 风险及建议 |
| --- | --- | --- |
| 高 | `flow.proactive` 被 [`registry_bootstrap.py`](../../zhiyin-src/template/zhiyin-boot/zhiyin_boot/registry_bootstrap.py) 要求存在，但通知 Worker 实际读取 `notify.stall.title/body`；[设计文档](../../docs/职引-完整设计文档.md) 也注明流程尚未接入。 | 编辑该提示词不会改变用户收到的提醒。明确采用模板通知还是模型生成，并使启动门禁与调用点一致。 |
| 高 | `task.plan.todos` 正文要求“产出一个数组”，实际 [`TodoSuggestions`](../../zhiyin-src/template/zhiyin-business/zhiyin_business/contracts/ai_tasks.py) 要求顶层对象 `{"items": [...]}`。 | 模型遵循文字要求时可能违背契约。以契约为准改写唯一顶层结构。 |
| 中 | `core.system` 统一称调用者为“职业顾问”，强调接住用户和每轮下一步；九项页面任务也加载它及 `guide.closing`。 | 角色身份与页面内容职责混杂。提取共同真实性规则，并分别制定对话与页面任务指令。 |
| 中 | Agent 缓存键只含角色、环节、任务码和工具开关，不含提示词内容或版本；配置重载接口只重装环节、布局、采集规则等快照。 | 数据库改了提示词后，已缓存的 Agent 可能继续用旧指令。增加版本或内容指纹，变更时重建 Agent。 |
| 中 | `PromptSpec.params` 可存温度、超时、重试；当前引擎构造模型时只读取 `temperature`。 | 配置值可能被误认为已生效。列出已消费参数并建立校验。 |
| 低 | 采集角色正文含一处字面量 `\n`。 | 文本格式缺陷。加入转义残留静态检查。 |

当前主动提醒文案会展示距上次关键动作的天数，而总纲避免“你已经 X 天没……”式施压。两者不完全同句，但应以用户实际看到的投递文案统一产品口径。

### 5.3 版本生效限制

生产环境首次导入后以数据库动态资源为准；仓库文件变更不会自动覆盖旧库值。启动时会报告文件与数据库漂移，强制重导属于独立运维动作。再加上 Agent 缓存，**文件已更新、数据库已更新、运行实例已使用新提示词**是三个不同状态，迭代发布应分别验证。

## 6. 建议的版本迭代

### V1.1：契约和调用点对齐

修正 `task.plan.todos` 顶层结构说明，清理转义残留；为全部启用提示词建立“`code` → 调用点 → 契约或展示面”清单；对无实际调用点的条目明确停用或接入计划；检查 `params` 是否被调用方消费。

**验收：**启用配置均有明确消费者，任务提示词与结构化契约不冲突，静态门禁通过。

### V1.2：按场景拆分共同指令

共同层只保留真实性、证据、用户自主决策和输出纪律；对话环节使用接话与收尾规范；页面任务使用字段、缺数据处理和篇幅规则；主动提醒单独管理触发规则与投递文案。

**验收：**以同一批输入分别测试五环节和九项任务。页面任务无无关聊天话术，对话轮次能自然续接。

### V1.3：可追溯发布和对照评测

每次模型调用记录提示词版本或内容指纹、模型路由、参数、契约版本与结果。准备匿名固定场景，覆盖情绪性求助、连续点选、画像不足、外部事实缺失、方向改选、任务停滞、重复消息和页面任务缺数据。旧版与候选版使用相同输入及模型条件，对比结构化通过率、无依据结论率、重复追问率、有效下一步比例、响应时间和人工盲评。

**验收：**候选版达到预先确定的阈值；在文件、数据库、运行实例三个层面核实同一版本生效；保留可回退的上一版。

## 7. 建议处理顺序

1. 固定唯一测试入口，核对 Docker 镜像、main 提交和 OpenAPI 版本；在统一版本上重跑 35 项回路。
2. 根据重跑结果定位业务失败；补齐源码根 README 的设计文档链接，使全量静态测试恢复通过。
3. 处理 `task.plan.todos` 契约冲突、`flow.proactive` 的无效配置及嵌入供应商标识。
4. 建立提示词版本、实际生效核验和 Agent 缓存失效机制，再用固定场景对照模型输出。

截至本报告完成时，以上均为**建议**，源码和提示词尚未按 V1.1～V1.3 修改。

## 8. 真实服务与当前部署的深入验证

### 8.1 模型、嵌入与向量库

在已有环境变量和 Docker 配置基础上发起最小真实请求，没有在命令或本文中重写密钥。结果如下：

| 链路 | 实际配置与结果 | 结论 |
| --- | --- | --- |
| 对话模型 | DeepSeek 兼容接口，配置名 `deepseek-chat`；请求 HTTP 200，返回非空 JSON；响应中的模型名为 `deepseek-flash` | 现有别名当前可用；发布记录应保存请求名和响应名，避免版本归因不清 |
| 文本嵌入 | DashScope 的 OpenAI 兼容 `/embeddings` 接口，`qwen3.7-text-embedding-flash`；两条输入均返回向量，维度为 1024 | 用户提供的调用思路与现有配置相符；[阿里云官方文档](https://help.aliyun.com/en/model-studio/embedding)说明兼容接口及维度 |
| 入库检索 | 当前源码的嵌入 Gateway 生成 1024 维查询向量，`knowledge` 命名空间在 pgvector 中检索到 3 条理论片段；库内 6 条已有向量均为该模型、1024 维 | 从供应商请求到实际召回的链路连通；这不能证明召回质量或覆盖率 |

嵌入配置在注册表中使用 `provider_code=doubao`，实际模型和地址却属于 DashScope；实现类也叫 `DoubaoEmbeddingGateway`。这不妨碍上述调用成功，但会误导监控、排障和模型迁移。DeepSeek 当前 [Chat Completions 官方文档](https://api-docs.deepseek.com/api/create-chat-completion/)可作为后续核对接口字段的基准；本次可用性结论来自实测，不依赖文档推断。

### 8.2 最新源码经 Agno 引擎的真实输出

直接使用当前 main 的提示词注册表与 Agno 引擎调用真实模型，输入均为合成场景，未写业务数据库。采集场景 `CollectOutput` 合约 1/1 通过，约 3 秒返回 `major`、`grade` 字段及可继续回答的选项，输出未降级。待办建议 `task.plan.todos` 对相同输入独立调用 3 次，3/3 均返回合约要求的顶层 `items` 对象，条目数分别为 1、3、3。缺少画像事实的职业匹配任务返回空 `cells`、空 `ranking`，并说明数据不足，没有虚构匹配分数。

这些结果表明当前模型加结构化约束可以在少量样本中抵消 `task.plan.todos` 的文字冲突；它**没有消除提示词与契约不一致的设计风险**。三次输出条目数量不同，也提示待办任务应按稳定性和可执行性制定固定评测集，而不只看 JSON 合法性。

### 8.3 运行实例与 main 不一致

当前机器上的地址解析会触达不同 API：`127.0.0.1:8000` 的 OpenAPI 只有 15 条路径、版本 `0.1.0`，注册路由返回 404；`localhost:8000` 与 Docker 容器内部均有 41 条路径、版本 `1.0.0`。当前源码契约有 44 条路径。因此，测试入口必须记录**完整主机名、OpenAPI 指纹和容器镜像**，不能只写端口。

当前 `zhiyin-flash` 镜像创建于 2026-09-23 00:47:46 UTC。容器里的 `PostgresAssetRepository` 没有 `mark_needs_recompute` 方法，而已拉取的 main 源码具有该方法。这是镜像落后于源码的直接证据。容器 `/healthz` 同时报告 `degraded`，需要在统一部署版本后重新核对依赖状态。本轮按“只出文档”的要求，没有重建或重部署服务。

### 8.4 Docker 端到端回路：27/35

使用仓库现有 [`loop_verify.py`](../../zhiyin-src/template/tests/e2e/loop_verify.py) 对 `localhost:8000` 做合成账号测试，35 项中 27 项通过。画像写入、报告、三个计划、行动计划、日历节点、任务完成、初次缓存等主路径已有通过证据。八项未通过：

1. 历史报告第 2 版读取为空。数据库中存在版本 1～4 的资产版本记录，但内容记录只有版本 1、3、4。
2. 画像改变后未标记关联资产 `needs_recompute`。
3. 重算后未向用户披露结论变化。
4. 缺口声明未进入决策环节；容器接口对 `option_id` 返回 422，认为它是额外字段。
5. 勾选行动任务后，日建议缓存仍命中旧值。
6. 导入学业数据后，日建议缓存仍命中旧值。
7. 完成任务后的下一轮仍停留在行动环节，未进入复盘。
8. 相同 `client_msg_id` 重放仍写入重复历史。

另用当前容器完成三轮对话：采集、采集、诊断均返回 HTTP 200，形成 5 个画像字段和 3 节报告。第一轮面对合成用户“我是不是很差劲”的表达，没有直接回应情绪问题；最新源码的独立采集探针能作出回应。由于部署版本不同，这一差异应作为**版本对照线索**，不能只归因于提示词。上述回路在 Docker 数据库留下合成测试数据；测试 JSON 输出保存于本机临时目录 `zhiyin-loop-audit-20260924.json`。

### 8.5 后续验收条件

每轮验收应同时记录镜像构建版本、OpenAPI 路径及健康状态，并以同一版 main 重跑 35 项回路，逐项定位仍然存在的业务失败。提示词候选版须在相同模型、输入和业务状态下比较。这样才能把部署差异、业务逻辑缺陷和提示词效果分开计量。
