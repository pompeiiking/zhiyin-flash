## 2. 问题与证据

- 20 并发子请求 P95 为 773 ms，稳定通过。
- 50 并发 P95 为 2.27 s、P99 为 14.64 s，4.678% 请求超过 5 s。
- 100 并发复测 P95 为 29.56 s，出现 101 个失败子请求和 65 个 30 s 超时。
- 失败时容器未重启、未 OOM，Mock LLM 平均响应约 95 ms；证据更符合应用进程内部排队。
- 原应用在每个 ASGI 进程内同时启动 PostgreSQL 调度器和业务 Worker，直接扩容会导致后台任务重复执行风险。

**优化假设：** 用两个独立 API 进程分担当前的请求排队，同时把调度器与后台
Worker 收敛到一个单例服务，并把每进程数据库连接池纳入部署参数。

## 3. 修改内容

- 新增 `docker-compose.perf.yml`：API 可 `--scale`，不固定容器名和宿主机 8000 端口；后台服务单例运行。
- Nginx 通过 Docker DNS 解析 `zhiyin-flash`，日志增加实际 upstream 地址、上游耗时和总耗时。
- 保留 SSE 的 HTTP/1.1、长超时与关闭代理缓冲语义；不开启非幂等 POST 重试。
- 新增 `ZHIYIN_RUN_IN_PROCESS_BACKGROUND`，API 副本可关闭 lifespan 中的调度器和 Worker。
- 新增 `python -m zhiyin_boot background`，在单例进程内运行调度器与全部后台 Worker。
- 新增 `--workers`，仅表示 Uvicorn HTTP 进程数，供 R1W2/R2W2 对照使用。
- 新增 `ZHIYIN_POSTGRES_POOL_MIN_SIZE` 和 `ZHIYIN_POSTGRES_POOL_MAX_SIZE`，同一进程所有仓储继续共用一个池。
- 增加设置、连接池冲突、API 关闭后台任务、Compose 扩容约束和 Nginx SSE/upstream 日志的回归测试。

**明确未修改：** 业务算法、SQL、数据库表、Redis 键口径、AI 提示词、JMeter 05 脚本和固定 Mock 实现。

## 4. 部署约定

| 项目 | 值 |
| --- | --- |
| 基础 Compose | `docker-compose.perf.yml` |
| 后端服务名 | `zhiyin-flash` |
| PostgreSQL 服务名 | `postgres` |
| Docker 网络键 | `zhiyin-flash-net` |
| 后台单例服务 | `zhiyin-background` |
| 对外测试入口 | 现行公网/Nginx 入口，禁止直连某个 API 容器 |
| 首选候选 | R2W1：2 API 副本 × 每副本 1 HTTP worker |
| API 池上限 | R2W1 每进程 5，API 合计 10 |
| 后台池上限 | 2 |

启动前由成员 C 先设置：

```bash
cd ~/apps/zhiyin/release
export TEST_COMPOSE_FILE=docker-compose.perf.yml
export TEST_IMAGE_TAG=opt-佟彤-v1
export TEST_REPLICAS=2

sudo env \
  ZHIYIN_IMAGE_TAG="$TEST_IMAGE_TAG" \
  ZHIYIN_WEB_WORKERS=1 \
  ZHIYIN_API_POOL_MAX_SIZE=5 \
  ZHIYIN_BACKGROUND_POOL_MAX_SIZE=2 \
  docker compose -f "$TEST_COMPOSE_FILE" up -d \
  --no-build --force-recreate --remove-orphans \
  --scale zhiyin-flash="$TEST_REPLICAS"
```

Compose 展开和容器状态核对：

```bash
sudo env ZHIYIN_IMAGE_TAG="$TEST_IMAGE_TAG" \
  docker compose -f "$TEST_COMPOSE_FILE" config --quiet
sudo env ZHIYIN_IMAGE_TAG="$TEST_IMAGE_TAG" \
  docker compose -f "$TEST_COMPOSE_FILE" ps
sudo env ZHIYIN_IMAGE_TAG="$TEST_IMAGE_TAG" \
  docker compose -f "$TEST_COMPOSE_FILE" logs --tail=100 zhiyin-flash zhiyin-background web
```

PostgreSQL 总量门禁：

```bash
sudo docker exec zhiyin-flash-postgres psql -U zhiyin -d zhiyin -c "SHOW max_connections;"
sudo docker exec zhiyin-flash-postgres psql -U zhiyin -d zhiyin -c \
  "SELECT application_name, state, count(*) FROM pg_stat_activity GROUP BY 1,2 ORDER BY 1,2;"
```

必须满足：

```text
API副本数 × HTTP worker数 × API单进程池上限
+ 后台服务池上限
+ 至少20条运维/其他连接预留
< max_connections
```

## 5. 对照矩阵与正式验收

| 组合 | API 副本 | 每副本 HTTP worker | 每进程 API 池 | 用途 |
| --- | ---: | ---: | ---: | --- |
| R1W1 | 1 | 1 | 5 | 新部署形态的单进程对照 |
| R1W2 | 1 | 2 | 5 | 验证单容器多进程 |
| R2W1 | 2 | 1 | 5 | 首选正式候选 |
| R2W2 | 2 | 2 | 2 | 仅在 CPU/内存/连接充足时补测 |
| R3W1 | 3 | 1 | 3 | R2W1 不达标且仍有资源余量时补测 |

每个组合使用同一份 `05-sustained-mixed-load.jmx`，依次运行 V05、20、50、100 并发。
前一档未通过时不得进入下一档。

验收线：

- 50 并发完整 300 s；错误率 0；P95 不高于 2.27 s；超过 5 s 比例小于 1%。
- 100 并发完整 300 s；不触发安全停止；错误率不超过 1%；无普通请求 30 s 超时；P95 低于 5 s。
- Nginx 日志出现所有 API 副本的 `upstream_addr`，任一副本请求占比不得长期高于 70%。
- 无容器重启、OOM、数据库连接耗尽、SSE 退化或后台任务重复执行。

## 9. 已知风险与观察项

- 多副本未必提高性能；如果热点实际在会话逻辑、外部情报链路或 PostgreSQL，应把证据交给成员 A。
- R2W2/R3W1 会增加 Python 进程内存、数据库连接和同机 Mock 资源竞争，不得跳过余量检查。
- 后台单例不是高可用方案；本阶段优先保证不重复执行。后续如要多副本后台任务，需先增加数据库领取锁/租约。
- 不以调大 JMeter 或 Nginx 超时冒充容量提升。
