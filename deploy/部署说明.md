# 职引 · 重新部署说明

这份包的目标只有一个：**换一台机器（或清空数据卷）重新部署一遍，整体跑通。**

整个过程是四步，但**顺序不能换** —— 先把数据迁进去，再起服务。原因写在第二节。

## 零、开跑之前：两处必须确认的事

这两条都属于"不报错的错" —— 没改也能起来，只是在运行时悄悄少东西。所以先列在最前面。

| 要改什么 | 在哪 | 不改会怎样 |
| --- | --- | --- |
| **令牌签名密钥**换成随机串（≥32 字符） | `.env` 的 `ZHIYIN_AUTH_JWT_SECRET` | 出厂值是占位串，等于签名密钥是公开的：任何人都能伪造登录令牌。`deploy.ps1` 会拦住这一条并要求你改完再跑 |
| **嵌入模型能不能连上** | `.env` 的 `ZHIYIN_EMBEDDING_*`（出厂配置指向**本机 Ollama**：`host.docker.internal:11434` + `qwen3-embedding:4b`） | 连不上时对话照常，但那几轮会**没有知识库依据**（日志有一行 `知识检索失败，本轮按"没有依据"处理`）。要恢复只有两条路：装 Ollama 并 `ollama pull qwen3-embedding:4b`，或改成云端嵌入（`ZHIYIN_EMBEDDING_BASE_URL` / `ZHIYIN_EMBEDDING_MODEL` 指向你的供应商） |

生成一条随机密钥：

```powershell
powershell -NoProfile -Command "[guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')"
```

> 换了密钥之后，**已经发出去的登录令牌全部失效**（用户重新登录一次即可），
> 画像、方案、报告、对话这些数据都不受影响 —— 它们不以密钥加密，只以密钥验身份。
>
> 嵌入维度也是"换了就得重建"的一类：不同模型的向量不在同一个空间里。
> 换嵌入模型后由 `vector_sync` Worker 全量重嵌（进度记在 `infra_vector_sync_state`），
> 不需要手工清库。

## 一、四步

```bash
docker compose build
docker compose up -d postgres redis
docker compose run --rm zhiyin-flash python scripts/migrate_db.py import \
  --dsn postgresql://zhiyin:zhiyin@postgres:5432/zhiyin --in /migration/migration.json
docker compose up -d
```

Windows 上等价于一条命令（脚本内容就是上面四步）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy\deploy.ps1
```

> 脚本文件是 **UTF-8 带 BOM**：Windows PowerShell 5.1 对无 BOM 的 UTF-8 会按本机
> 代码页解码，中文标签变成乱码之后脚本可能整段被当成字符串回显——**四步一步都没跑，
> 却打印得像成功**。用 `powershell.exe`（5.1）跑时务必保留 BOM，或直接用
> PowerShell 7（`pwsh`）。改这个文件请用「UTF-8 with BOM」保存。

起来之后：

| 地址 | 是什么 |
| --- | --- |
| http://127.0.0.1:5173 | 前端站点：首页 → 进任务 → 对话 → 工作台 → 报告 |
| http://127.0.0.1:8000/api/v1/docs | 后端接口文档 |
| http://127.0.0.1:8000/healthz | 装配报告（能力位 wired / skeleton 一览） |

**从零开始**（连数据卷一起清掉，模拟一台全新机器）先执行 `docker compose down -v`，
再跑上面四步。`down -v` 会删掉 `zhiyin-postgres-data` / `zhiyin-redis-data` 两个卷，
是**不可恢复**的删除，只在确认要重来一次时用。

## 二、为什么必须先迁移：空库丢的是"补不回来"的那部分

服务启动时会把 `data/registry/*.json` 导进库，所以文案、提示词、编排规则、
理论卡、产出契约这些**能从文件长回来**。下面这些长不回来：

| 表 | 里面是什么 | 空库之后会怎样 |
| --- | --- | --- |
| `infra_ai_provider` | AI 供应商，**含 api_key** | 密钥没了 |
| `infra_ai_model` | 模型清单 | 同上 |
| `infra_ai_route` | 场景 → 模型的路由 | 同上 |
| `infra_runtime_config` | 装配口径（门禁 / 归属） | 文件可以补回 |
| `biz_*` / `ai_task_result` / `vec_record` | 账号、画像、会话、资产、报告正文、向量 | 全丢 |

**模型密钥为什么只能靠迁移**：按"配置入库"的口径，密钥刻意只存库、不写 `.env`
（`.env` 里那几个 `ZHIYIN_LLM_API_KEY` 是首次开机的种子，本机那份是空的）。
所以"空库 + 一份 `.env`"起来之后模型是不可用的 —— 这就是"空库没有核心策略"的
实际含义。迁移文件里 `infra_ai_provider.config.api_key` 是唯一的那一份。

> 迁移文件里含密钥。要把它发给别人时加 `--redact-secrets` 重新导一份，
> 部署时再用 `.env` 的 `ZHIYIN_LLM_API_KEY` 补一次。

## 三、这份迁移文件里有什么

**上线用的交付包只带策略、配置与向量** —— 新环境起来是一个干净的站，
没有上一个环境的账号、画像与对话：

```bash
python scripts/migrate_db.py export --dsn <源库> --out migration.json \
  --include-vectors
```

| 组 | 张数 | 内容 |
| --- | --- | --- |
| 策略与配置（默认导出） | 8 | AI 供应商 / 模型 / 路由、装配口径、功能开关、运营改过的动态资源、提示词、编排规则 |
| 向量（`--include-vectors`） | 2 | `vec_record`、向量同步进度 |

**整机搬家**（把现有环境原样复制到另一台机器）才加 `--include-users`，
这时会多出 16 张用户数据表：账号与凭据、画像、行为、记忆、**会话逐轮原文**、笔记、
教务快照、会话、资产、日历、时间线、AI 任务产出。

> 这 16 张是被 `tests/test_schema_migration.py` 逐一钉住的：建出来的每张表都必须在
> 「迁移 / 不迁并写明理由」里有登记。加表忘了登记，代价是搬家时**静默少数据**
> （`biz_conversation_turn` 就这样漏过一次，症状是"这条会话没有逐轮原文"）。

**刻意不迁**的四张表（`infra_auth_session`、`orc_event_outbox`、`orc_schedule_job`、
`orc_notification`）都是**旧环境的一次性运行态**：登录令牌换环境后重新登一次即可，
出站箱里的待投递事件与已发出的提醒在新环境重放只会变成重复打扰。
判据不是"这张表重不重要"，而是"这份内容在新环境还有没有意义"。

## 四、部署后自查

```bash
# 1) 迁移是否逐字落地。注意它比的是**每一行内容**，不是行数 ——
#    行数对得上但密钥为空，也会被判为未通过。
docker compose run --rm zhiyin-flash python scripts/migrate_db.py verify \
  --dsn postgresql://zhiyin:zhiyin@postgres:5432/zhiyin --in /migration/migration.json

# 2) 装配现状与里程碑门禁
docker compose exec zhiyin-flash python -m zhiyin_boot --check --phase=2

# 3) 启动日志里不该出现这几行
docker compose logs zhiyin-flash | grep -E "不一致|失败|缺少"
```

第 1 条的期望输出是 `核对通过：迁移文件里的每一行都逐字落进了目标库。`；
第 2 条的期望是 `"passed": true`。

启动日志里出现下面任一行都代表还没对齐，不要当成噪声：

| 日志 | 含义 |
| --- | --- |
| `动态资源与 data/registry 不一致` | 库里的口径与仓库里的文件不同。以库为准；确认要对齐时给启动命令加 `--resync-registry` |
| `装配口径 assembly.* 与 data/registry 里的种子不一致` | 同上，作用于门禁与归属 |
| `读取库里的 AI 配置失败` | 库连不上或表结构不对，此时会退回 `.env` 的种子值 |

## 五、数据分三层，别把该留在库里的东西塞进 `.env`

| 层 | 放什么 | 存在哪 | 丢了会怎样 |
| --- | --- | --- | --- |
| 进程内装载 | 环节口径 / 文案 / 编排 / 采集规则 / 提示词 / 读缓存策略 | 启动时从库读一次，`POST /app/config/reload` 原地替换 | 重启后重新读一次 |
| 读缓存 | **可重建的读模型**（工作台聚合 / 报告正文 / 理论卡） | Redis | 下一次读变慢，结果不变 |
| 长期保存 | 账号 / 画像 / 会话逐轮原文 / 资产 / 笔记 / 教务快照 / 日历 / 时间线 / 向量 | PostgreSQL + pgvector | **不可恢复**（只能靠本节第一段的迁移文件） |

三个当场可查的落点：

- `/healthz` 的 `cache` 段 —— 有哪几片缓存、各自 TTL、被哪些事件失效、命中率多少。
  冷启动 `hit_rate` 是 `null` 属正常（还没有请求），策略列得出来就说明装载成功；
- 启动日志里的动态资源对账 —— 库与 `data/registry/*.json` 不一致会直接打印差异；
- `docker compose exec zhiyin-flash python -m zhiyin_boot --check --phase=2` ——
  `cache` 段与装配状态同源，`--check` 也打印它。

写侧从不写缓存：用户的每句话、每次勾选、每次导入都**先落库**，写完整片失效。
所以"改了画像界面上还是旧的"不该出现 —— 出现就是某条写路径漏了失效事件，
而不是缓存本身的问题。

## 六、开发期：改代码不用重建镜像

上面四步是**部署**口径：镜像里装的是构建那一刻的代码（`pip install .`，非可编辑）。
开发时每次改一行都重建镜像（本机实测约 3 分钟）没有必要，用叠加层把源码挂进去即可：

```bash
# 起开发态（源码挂载 + 热重载）
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d

# 收工时回到部署态（镜像里那份代码）
docker compose up -d
```

三点要知道的：

1. **不带 `-f docker-compose.dev.yml` 时，行为与部署完全一致** —— 这是刻意的：
   默认那条命令必须跑镜像里那份代码，不能悄悄换成工作区（否则"我本地是好的"会变成
   一种没人说得清的状态）。
2. **开发态跑的就是你工作区那份代码，未提交的改动也会被跑** —— 这正是它快的原因，
   但也意味着别拿它当验收环境。验收仍然用不带叠加层的那条命令。
3. **只覆盖后端**。前端是 nginx 托管的静态构建产物，挂源码不会重新构建；
   改前端要么 `cd zhiyin-src/template/zhiyin-web && npm run dev`（先 `docker compose stop web`，
   两者都用 5173），要么重建 web 镜像。

> **一个踩过的坑：别只 `docker compose up -d web`。**
> `web` 的 `depends_on` 里有 `zhiyin-flash`，而基础文件与叠加层的配置不同 ——
> 那条命令会把**后端**按基础文件重建，也就是把它从开发态悄悄拉回部署态、
> 而且跑的是**镜像里那份旧代码**（实测：重建 web 之后，后端缺了当时新加的工具，
> 一整轮核验其实在测旧后端）。
> 要重建前端就带上叠加层：
>
> ```bash
> docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d web
> ```

**查现在是哪一态**（两条都不用猜）：

```bash
# 命令里有 --reload、且挂载里有源码 → 开发态
docker inspect -f '{{json .Config.Cmd}}' zhiyin-flash
docker inspect -f '{{range .Mounts}}{{.Destination}} {{end}}' zhiyin-flash

# 容器里 import 的是哪一份代码：/work/... 是挂载（开发态），
# /usr/local/lib/.../site-packages 是镜像里那份（部署态）
docker exec zhiyin-flash python -c "import zhiyin_boot; print(zhiyin_boot.__file__)"
```

改代码之后：`.py` 由热重载自动生效（约 1 秒）；改 `data/registry/*.json`（提示词 / 文案 /
路由规则这类**动态资源**）不会自动生效 —— 它们以库为准，要重导一次并重启：

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  run --rm --no-deps zhiyin-flash python -m zhiyin_boot --resync-registry --check
```

> 热重载只监听七个包目录（`--reload-dir`）。默认是监听整个工作目录，而这个挂载里带着
> Windows 的 `.venv` 与 `build/` —— 实测 5875 个 `.py` 文件，轮询一遍要 20 秒，
> 表现就是"改了代码却像没生效"。只列包目录后是 218 个文件、约 0.65 秒一轮。
