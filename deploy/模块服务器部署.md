# 模块平台服务器交付说明

交付对象：佟。平台接口和业务边界以[完整设计文档](../docs/职引-完整设计文档.md)为准。
此说明交付部署材料；本机执行器不会远程发布生产环境。
**v2 部署与维护优先阅读本页末尾“v2 交付与运行手册”。** 原有章节保留首版生产安装方式；
原打包文件名和验收记录属于其对应版本，不能据此认定本轮已经完成服务器部署。

## 发布件

每次交付同一个完整 Git SHA 对应的源码包、两个应用镜像及测试记录。
源码包必须包含 Dockerfile、deploy/compose.platform.yml、deploy/Dockerfile.platform-web、
deploy/nginx.platform.conf、全部 Python 包和 zhiyin-modules 资源、前端源码与 package-lock.json。
本次本机测试的提交号和结果见[模块平台验收记录](模块平台验收记录.md)。
当前交付文件名和 SHA256 见 `release/source-manifest.json`、`release/image-manifest.json`，
另有 `release/module-platform-delivery.zip` 提供最终验收记录。先解压源码，再把补充包解压到源码根目录；
补充包不更换应用代码或镜像版本。以补充包中的最终验收记录为准，源码中的记录保留构建时状态。

源代码也可直接从团队仓库检出该提交。不要用尚未提交的开发目录充当生产版本。
镜像分别命名为 `zhiyin-platform-api:SHA` 与 `zhiyin-platform-web:SHA`。
从有这两份镜像的机器导出：

```sh
docker image save -o module-images.tar zhiyin-platform-api:SHA zhiyin-platform-web:SHA
```

镜像不包含模型密钥或本机 `.platform/`。私密环境配置须在目标机器另外建立。

## 配置与启动

1. 目标机器安装 Docker Engine 和 Compose，准备上述代码或源码包。
2. 将 deploy/platform.env.example 复制到私密目录（如 /srv/zhiyin-secrets/platform.env）。
3. 填入提交 SHA、随机数据库密码、至少 32 字符的随机 JWT 密钥和模型密钥。
4. 保持 PLATFORM_ENV=production。更换端口时同时调整服务器反向代理。
5. 如有镜像包，先运行 `docker image load -i module-images.tar`，再执行：

```sh
docker compose --project-directory . --env-file /srv/zhiyin-secrets/platform.env -p zhiyin-server -f deploy/compose.platform.yml up -d --no-build
```

没有镜像包时，用同一命令的 `up -d --build` 从确定提交构建。
Compose 的应用端口绑定本机回环地址，由服务器上的 HTTPS 反向代理转发到前端端口。
浏览器通过前端的 /api/ 反代访问后端。PostgreSQL 和 Redis 只开放在该 Compose 网络内。

三个关键检查：

```sh
curl http://127.0.0.1:8080/healthz
curl http://127.0.0.1:8080/version.json
docker compose --project-directory . --env-file /srv/zhiyin-secrets/platform.env -p zhiyin-server -f deploy/compose.platform.yml ps
```

前后端 revision 必须等于同一个交付 SHA，environment 应为 production。
通过平台接口读取数据库中的模型路由并做真实调用后，才能判定模型可用；仅健康检查不代表模型验收。

## 管理员与模块配置

把初始管理员密码安全设置到宿主机 PLATFORM_ACCOUNT_PASSWORD 环境变量，再执行：

```sh
docker compose --project-directory . --env-file /srv/zhiyin-secrets/platform.env -p zhiyin-server -f deploy/compose.platform.yml exec -T -e PLATFORM_ACCOUNT_PASSWORD api python scripts/module_admin.py OWNER --role admin
```

生产不使用 `--seed`，不导入测试账号。运行后清除宿主机的临时密码变量。
OWNER 登录 /developer 后设置模块授权及智能体工具范围；新模块默认停用。
公开注册只能得到普通用户身份。生产环境禁止真实测试预览和测试发布请求。

需要搬迁既有配置时使用项目原有数据库迁移工具；模型路由由数据库当前记录决定。
不要直接复制本机测试数据库。模块权限表可以迁移，发布队列和租约必须留在原环境。

## 升级和恢复

升级前保留数据库备份、上一组镜像标签和私密环境文件。先在独立测试环境验证指定提交。
升级时只修改 PLATFORM_REVISION，再启动整套前后端应用。
失败时恢复上一组镜像标签并重新启动，随后核对两个版本接口和用户关键业务。
数据库迁移只增加兼容字段和表；恢复镜像不撤销数据修改，也不等于数据库恢复。
不要通过删除数据卷处理启动失败。发布日志和数据库备份应另外保存。

## v2 交付与运行手册（当前流程）

### 1. 交付范围与服务器环境

尚未提供目标云服务器和凭据，因此这里是可执行部署材料，**不代表已经完成云部署**。
代码更新仍以整套应用的蓝绿槽切换实现，模块在职引平台内使用；不为每个模块建立独立数据库或容器。
上传与自动执行只面向内部可信开发团队，公开注册不能取得开发、项目运行或发布权限。

当前自动化执行器固定管理 `staging` 测试环境及回环端口 5175/8015，控制面是 5174/8014。
在服务器复用该流程时，应为团队单独部署工作台和测试环境，并经服务器 HTTPS 反向代理暴露需要的入口。
现有 `production` 环境继续使用前述受控镜像部署；不能仅修改域名或一个环境变量，就宣称当前测试执行器支持生产自动发布。
将生产纳入自动化前需明确目标隔离、数据库兼容和恢复验收，并相应实现目标配置。

每次 v2 交付至少保留：

- 完整提交 SHA 对应的源码和镜像摘要；包括 `deploy/module_source_worker.py`、`module_executor.py`、
  `module_bluegreen.py`、`module_browser_gate.py`、`module_workflow_guard.py`、`start_module_workers.ps1`、
  `compose.platform.yml`、`compose.bluegreen.yml`、`nginx.slot.conf.template`。
- 全部模块源码、声明及测试；平台 `scripts/module_dataflow_acceptance.py`；OpenAPI 与生成的前端类型。
- 源码验收报告、发布任务、运行环境版本及真实模型验收结果，逐项标明实际执行范围。
- 单独交接的私密环境文件和执行器配置，不放入源码包或公开构建日志。

### 2. 迁移前备份（Linux 示例）

先暂停宿主机上的源码工作器与发布执行器，确保没有新写入任务正在交接；业务数据库备份仍需按团队恢复方案验证。
下面假定工作台与测试环境沿用标准容器名。容器名不同，应先从对应 Compose 项目 `ps -q postgres` 取得准确 ID，
不要把其他项目的数据库当作目标。

```sh
platform_backup="/srv/zhiyin-backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$platform_backup"
chmod 700 "$platform_backup"

docker exec zhiyin-module-workbench-postgres-1 pg_dump -U zhiyin -d zhiyin -Fc -f /tmp/workbench-before-v2.dump
docker cp zhiyin-module-workbench-postgres-1:/tmp/workbench-before-v2.dump "$platform_backup/workbench.dump"
docker exec zhiyin-module-staging-postgres-1 pg_dump -U zhiyin -d zhiyin -Fc -f /tmp/staging-before-v2.dump
docker cp zhiyin-module-staging-postgres-1:/tmp/staging-before-v2.dump "$platform_backup/staging.dump"
docker exec zhiyin-module-staging-redis-1 redis-cli --rdb /tmp/staging-before-v2.rdb
docker cp zhiyin-module-staging-redis-1:/tmp/staging-before-v2.rdb "$platform_backup/staging.rdb"
```

用 `pg_restore --list` 检查两个 dump 可读，并在隔离库进行恢复演练。Windows 同样采用容器内输出文件后
`docker cp` 的方式，避免 PowerShell 文本重定向破坏二进制 dump。

同时复制工作台/测试环境私密配置、执行器 JSON、`state_directory/bluegreen/`、执行器日志到受限备份目录。
对执行器受控仓库运行 `git bundle create PATH_TO_BACKUP/platform-source.bundle --all`，保存候选引用和已安装版本历史。
通过 `docker image save` 保留当前与上一已成功版本的 API/Web 镜像，不仅记录一个可变标签。
工作台数据库包含上传 ZIP 与验收历史，应整库备份；恢复后的旧租约和队列不能直接在另一环境开始执行。

独立生产项目的备份可复用同一方法，先取得其准确数据库容器：

```sh
platform_pg_id=$(docker compose --project-directory . --env-file /srv/zhiyin-secrets/platform.env -p zhiyin-server -f deploy/compose.platform.yml ps -q postgres)
test -n "$platform_pg_id"
docker exec "$platform_pg_id" pg_dump -U zhiyin -d zhiyin -Fc -f /tmp/production-before-v2.dump
docker cp "$platform_pg_id:/tmp/production-before-v2.dump" "$platform_backup/production.dump"
```

### 3. 配置受控源码仓库和两个执行进程

为执行器单独建立完整 Git 克隆，例如 `/srv/zhiyin-module-source`。它必须包含当前测试环境的已安装 SHA、
v2 基线 SHA 和候选引用。工作台的源码目录与执行器克隆分开，执行器不覆盖维护者尚未提交的修改。
当前已安装 SHA 在受控仓库中找不到时，应先核对并取回正确历史；不能用另一基线强行继续发布。

创建私密的 `/srv/zhiyin-secrets/platform-v2.json`，按服务器实际路径填写：

```json
{
  "repository": "/srv/zhiyin-module-source",
  "state_directory": "/srv/zhiyin-module-state",
  "compose_file": "/srv/zhiyin/deploy/compose.platform.yml",
  "bluegreen_compose_file": "/srv/zhiyin/deploy/compose.bluegreen.yml",
  "workbench_env_file": "/srv/zhiyin-secrets/workbench.env",
  "staging_env_file": "/srv/zhiyin-secrets/staging.env",
  "workbench_url": "http://127.0.0.1:8014",
  "source_base_commit": "REPLACE_WITH_COMMITTED_40_CHARACTER_SHA",
  "worker_id": "source-server-1",
  "browser_python": "/srv/zhiyin-browser-venv/bin/python",
  "rollout_strategy": "blue_green",
  "bluegreen_shared_network": "zhiyin-module-staging_default",
  "bluegreen_drain_seconds": 190,
  "bluegreen_observation_seconds": 10
}
```

工作台和测试环境分别使用数据库、Redis 数据及 JWT 密钥。工作台环境文件的 `ZHIYIN_EXECUTOR_TOKEN`
至少 32 字符，执行器从该文件读取；测试应用不持有控制面执行器凭据。
`source_base_commit` 替换为已提交的实际 SHA，不能使用占位文字或仅有工作区修改的版本。
两类执行进程需要 Git、Python 及 Docker 权限，应由宿主机服务管理器以固定工作目录启动，保存 stdout/stderr。
宿主 Python 使用 3.11 或以上；执行账号须能写入受控仓库和 `state_directory`，并读取私密环境文件。
交付时建立完整的 v2 JSON 配置。`setup_module_platform.py` 只提供首版本机初始化，生成的旧配置不包含
`source_base_commit`、`rollout_strategy` 和 `browser_python` 等 v2 必需项，不能直接作为服务器自动发布配置。

浏览器运行环境由维护者在可信宿主机安装，上传模块不能指定执行命令或 Python 路径。Linux 示例：

```sh
python3 -m venv /srv/zhiyin-browser-venv
/srv/zhiyin-browser-venv/bin/python -m pip install playwright
/srv/zhiyin-browser-venv/bin/python -m playwright install --with-deps chromium
```

安装系统依赖需相应宿主机权限；正式运行门禁只使用已经安装的 Chromium，不在任务内下载浏览器。
也支持 PATH 中已安装的 `chromium` 或 `chromium-browser`。Windows 使用已安装的 Microsoft Edge，
按模块开发说明建立 Playwright 环境，并将 `browser_python` 改为该环境的 `Scripts/python.exe` 绝对路径。
安装浏览器与启动工作器应使用同一宿主账号，保证 Playwright 缓存目录可读；更换服务账号后需核对该账号能启动浏览器。

`module_browser_gate.py` 是强制候选门禁：真实访问候选 Web，检查全部应用与技能的 normal、empty、error
预览、卡片、详情、可选对话组件、JSON 结果、窄屏与渲染错误。页面和 API 属于同一候选提交，
浏览器复用数据流验收的合成账号，不重新植入业务数据。只有候选 Web 同时连接内部网络和独立回环访问网络；
候选 API、PostgreSQL、Redis 不向宿主机发布端口，页面 CSP 禁止跨地址取数，不复用真实工作台数据库。
缺少浏览器、缺失输入报告、组件渲染异常或版本不一致均阻断发布。错误摘要可在工作台查看，完整 JSON 与截图
保存在 `state_directory/acceptance/jobs/任务编号/租约编号/`；候选清理包含浏览器 Web 及附加网络。
发布仅接受规则版本 `3` 且带相同候选 revision 的成功 `dataflow.browser` 报告，旧报告须重新验收。

### 4. 已有测试环境的首次蓝绿迁移

以下命令用于**已有** `zhiyin-module-staging` 数据库、Redis 和回环入口的环境，不能直接用于替换 `zhiyin-server` 生产项目。
首次安装测试环境时，应先按 `compose.platform.yml` 建立对应独立项目及完整 SHA 版本，再进行本节迁移。
确保 5176/8016、5177/8017 可用；它们只绑定回环地址。已有 5173 项目不在迁移范围内。

| 用途 | 默认回环端口 | 配置方式 |
| --- | --- | --- |
| 工作台 Web / API | 5174 / 8014 | `workbench.env` 的 `PLATFORM_WEB_PORT` / `PLATFORM_API_PORT`，并同步 `workbench_url` |
| 测试环境固定入口 Web / API | 5175 / 8015 | 当前宿主执行器固定使用，不能仅改环境文件 |
| 蓝槽 Web / API | 5176 / 8016 | JSON 可选 `blue_web_port` / `blue_api_port` |
| 绿槽 Web / API | 5177 / 8017 | JSON 可选 `green_web_port` / `green_api_port` |
| 一次性候选浏览器入口 | 动态空闲回环端口 | 门禁自动分配，避开平台端口；不用额外暴露候选 API 或数据库 |

`bluegreen_shared_network` 必须指向已存在的测试项目网络，且其中已有可通过 `postgres`、`redis`
服务别名访问的正确测试容器；它不是工作台网络。可用 `docker network inspect zhiyin-module-staging_default`
核对成员。修改槽位端口时四个值必须互不相同，不能占用现有项目、工作台或固定入口端口。

先从确认的 SHA 检出构建两个镜像。下面从已检出该 SHA 的源码根目录执行，使用测试环境文件而非生产文件：

```sh
platform_revision=REPLACE_WITH_FULL_40_CHARACTER_SHA
PLATFORM_REVISION="$platform_revision" docker compose --project-directory . --env-file /srv/zhiyin-secrets/staging.env -p zhiyin-module-staging -f deploy/compose.platform.yml build api web
python3 deploy/module_bluegreen.py --config /srv/zhiyin-secrets/platform-v2.json prepare-migration --revision "$platform_revision"
python3 deploy/module_bluegreen.py --config /srv/zhiyin-secrets/platform-v2.json activate-migration
python3 deploy/module_bluegreen.py --config /srv/zhiyin-secrets/platform-v2.json status
curl --fail http://127.0.0.1:5175/__platform_route
curl --fail http://127.0.0.1:5175/healthz
curl --fail http://127.0.0.1:5175/version.json
```

`prepare-migration` 预热槽位并保留原入口；`activate-migration` 才停止原 API/Web 并由网关接管固定端口。
首次端口交接可能短暂中断，必须单独验收；后续更新才使用已建立网关的蓝绿切换。
数据库与 Redis 留在原独立项目，两应用槽共享它们；真实数据验收另用临时候选库。
后台任务由唯一后台实例执行，新旧 API 槽都关闭后台轮询。

若宿主机在首次交接期间中断，先停止执行进程，核对没有另一人在恢复，再执行：

```sh
python3 deploy/module_bluegreen.py --config /srv/zhiyin-secrets/platform-v2.json recover-migration
```

恢复成功后原服务接回 5175/8015，保留业务数据。首次迁移已经完成时，不再使用该命令；按发布记录做正常版本回退。
CLI `status` 使用同一执行锁，发布常驻进程运行时请改用上面的 HTTP 状态接口查看。

确认迁移成功后，分别启动并托管：

```sh
python3 deploy/module_source_worker.py --config /srv/zhiyin-secrets/platform-v2.json
```

```sh
python3 deploy/module_executor.py --config /srv/zhiyin-secrets/platform-v2.json
```

源码工作器可使用不同 `worker_id` 并行领取任务，共享受控源码仓库与状态目录；发布执行器保持单实例。
两类进程自动启动与重启属于目标宿主机服务配置，不能把运行一次 `--once` 当作完成常驻部署。

Windows 可使用已交付的启动器，按准确配置路径和已安装的 Python 启动：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/start_module_workers.ps1 -Config C:/zhiyin-secrets/platform-v2.json -Python C:/Python311/python.exe
```

启动器核对蓝绿初始化日志和实际路由，隐藏启动两个进程，日志与 PID 位于 `state_directory/host-workers`。
重复运行会核对真实 Python、脚本和配置路径后复用现存进程；它不安装开机服务，也不会自动停止可疑 PID。
Linux 应将上面两个命令分别配置为宿主服务，并设置固定工作目录、执行账号和失败重启。

宿主重启后先确认 Docker、工作台和测试环境数据库/Redis 已恢复，再启动原配置对应的工作器。
已有蓝绿环境不重复执行首次迁移，不清空 `bluegreen/deployment.json` 或队列租约。
发布执行器领取待恢复任务后会核对实际网关、持久化 `pending` 状态与镜像，完成恢复再记录结果；
路由不属于日志中的 active/pending 版本时会拒绝继续，须保留现场核对。CLI `status` 也占用执行锁，
排障时先停空闲发布进程，或直接读取 HTTP 路由和任务记录。

### 5. 授权、阻断和故障维护

- 管理员为可信团队项目授权一次运行信任，按需启用 main 自动发布。源码包没有信任时只做静态接收。
  撤销信任会阻止后续执行并取消待发布任务，执行器切流前再次核对授权。
- main 通过门禁后可自动部署，feature 分支保留验收结果。新增模块安装后仍默认停用，需要目标环境管理员
  在“模块列表”授予读取/操作/智能体权限并启用；v2 不把工作台策略强行复制覆盖目标数据库。
- `configuration_required` 需要统一升级平台授权基线或调用方契约。没有强制绕过按钮；应由主项目维护者
  集成、验证并安装兼容基线，再从新基线提交新模块版本。
- 验收失败先区分源码错误与暂时性依赖故障；修改源码必须提高版本号。发布失败或已回退时，从版本详情重新验收，
  不要把“验收通过”当作已上线。发布排队、执行中、成功或状态未知时不开放原版本重验。
- 工作台状态栏的心跳属于源码工作器。发布任务长期停在 `queued` 时还需检查发布进程与其日志。
  `state_directory/logs` 保存完整脱敏日志，`bluegreen/deployment.json` 记录路由、镜像摘要与恢复阶段。
- 回退只使用曾成功安装的镜像和路由；不清空卷、不把数据库版本文字改成旧值、不重放不确定的写操作。
  新旧代码共存期间的数据库变更须兼容，真实数据恢复单独执行已验证的备份方案。

浏览器版本提示在新标签页打开新版，保留原页面输入。页面列表的已安装 SHA、网关路由及前后端版本接口应一致。
迁移、访问连续性、重启恢复、真实模型和用户业务确认分别保存证据；不能以镜像构建成功代替这些验收。

### 6. 已发布工作流的升级保护

工作流快照锁定每个节点的准确模块版本。目标环境存在已发布快照时，部署器会在切流前用候选代码检查
全部快照，包含模块存在性、版本、输入结构和绑定关系。该检查只读，不执行工作流或业务操作；不兼容即阻断发布。
报告保存在对应任务/租约的 `workflow-compatibility-槽位.json`，失败信息包含工作流与模块版本。

当前 API 的“发布”和“暂停发布”在事务内获取共享锁；宿主 `module_workflow_guard.py` 在检查及切流期间
持有排他会话锁，固定 PostgreSQL key 为 `741517501`。数据库控制表 `biz_module_runtime_revision`
只保存 `id=1` 的 `active_revision`；候选确认上线或恢复旧版本时由部署器在锁内更新。
旧 API 的 build revision 与该值不同，或正在部署时，发布/暂停接口立即返回 409，刷新后重试。
草稿保存不取得该部署锁，仍按 `expected_revision` 防止覆盖别人的修改。

从没有该协议的旧版本升级时，顺序如下：

1. 先升级工作台 API/Web 和宿主执行器文件，包括 `module_workflow_guard.py`。
2. 先发布一份**保持当前所有模块版本不变**的平台基线，包含新的 API、仓库和表结构。
   在该基线完成前暂不开展工作流发布或模块版本升级，避免旧 API 尚未实现共享锁。
3. 新 API 首次连接会执行幂等 DDL，建立控制表及初始空版本行；已有非空版本不会被启动覆盖。
   宿主辅助进程自身不建表，缺表会明确失败。首次蓝绿迁移只完成端口交接，随后仍须通过一次正常发布任务
   安装或确认上述基线，由部署器写入当前运行 SHA。
4. 核对下列只读结果与 `5175/__platform_route`、`5175/healthz` 及发布日志的当前 SHA 完全相同，
   再开放下一轮模块版本更新：

```sh
docker exec zhiyin-module-staging-postgres-1 psql -U zhiyin -d zhiyin -c "SELECT id,active_revision FROM biz_module_runtime_revision;"
```

该控制表不随业务迁移工具复制到另一环境；它必须描述目标环境实际运行的代码。禁止手工填入新 SHA 来跳过检查。
原工作台数据库没有应用切流时，初始空值保留兼容语义；测试环境正常发布完成后必须有准确的运行 SHA。

升级因旧快照版本被阻断时，工作流拥有者或管理员先在目标环境“数据编排”中暂停对应工作流发布。
暂停采用 CAS，仅清除 `published_revision`，草稿、历史快照和运行记录保留；新用户调用立即不可用。
模块更新完成后，修改草稿中的引用版本、保存形成新修订并通过预览，再发布新快照。
平台不会自动改写旧工作流的版本引用；回退应用同样要通过目标快照兼容检查。
