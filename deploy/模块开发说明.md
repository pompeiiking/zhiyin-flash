# 模块开发与测试发布

**新接入优先阅读本页“v2：上传、自动验收与维护”章节。** 第 1—6 节保留代码仓库接入的历史操作，
仍供主项目维护和本地开发参考；涉及上传、权限、候选验收、配置同步和发布方式时，以 v2 章节为准。
业务与接口边界以[完整设计文档](../docs/职引-完整设计文档.md)第十五、十六节为准。
模块是团队内部经过审查的代码，随应用构建；依赖检查不能作为不可信代码沙箱。

## 1. 启动开发工作台

要求 Docker Desktop 可用，根目录已有 `.env`，其中配置 `DASHSCOPE_API_KEY`。
从仓库根执行：

```powershell
python deploy/setup_module_platform.py
```

该命令创建独立 Docker 项目 `zhiyin-module-workbench`，不操作当前 5173 项目。
工作台地址是 http://127.0.0.1:5174/developer，后端是 8014。
生成的本机配置位于 `.platform/`，已从 Git 和 Docker 构建上下文排除。
管理员账号 `admin`、开发者 `module_developer`、普通测试用户 `module_student` 的初始密码统一为 `123456`，配置保存在 `.platform/workbench.env` 的 `PLATFORM_ACCOUNT_PASSWORD` 中。所有账号只存在于隔离数据库。
部署后应自行更换测试凭据；工具重复执行保留已有凭据和业务数据。

真实数据库操作示例数据由管理员脚本初始化。需要授予已有账号角色时：

```powershell
docker compose --project-directory . --env-file .platform/workbench.env -p zhiyin-module-workbench -f deploy/compose.platform.yml exec -T api python scripts/module_admin.py ACCOUNT --role developer
```

只有拥有本机部署权限的人能执行初始化命令。公开注册不接收角色。

## 2. 创建与开发模块

在 `zhiyin-src/template` 中安装开发依赖，然后创建模块：

```powershell
python -m pip install -e ".[dev]"
python scripts/module_cli.py new my_card --name "我的功能" --owner "开发者姓名"
python scripts/module_cli.py check
python -m pytest -q zhiyin-modules
```

默认命令生成目录 `zhiyin-modules/zhiyin_modules/my_card/`，类型为 `hybrid`。

模块支持三种分类，使用 `--kind` 选择：

| 分类 | 用途与入口 |
|---|---|
| `application` | 在职引中作为完整功能独立展示；必须有首页卡片，可有详情，不声明智能体工具 |
| `tool` | 供智能体调用的技能；必须声明工具，不声明首页卡片或详情入口，可选对话展示组件 |
| `hybrid` | 同时提供应用入口与智能体工具，必须声明卡片和工具；脚手架默认类型 |

这些模块随整套应用构建安装，由平台配置控制启停，不为每个模块创建独立服务或容器。
`--parent` 可指定所属应用；省略时作为顶层模块。指定的父模块必须已存在且为
`application` 或 `hybrid`，不能自引用或形成循环。例如创建不带界面的技能：

```powershell
python scripts/module_cli.py new progress_skill --name "计划进度技能" --owner "开发者姓名" --kind tool --parent action_progress
```

`tool` 模板复制 `plan_progress_skill` 的后端、模拟数据和测试，不生成 Vue 文件或业务操作声明；
`application` 和 `hybrid` 模板以行动计划进度示例为基础。技能默认将校验后的 JSON 返回智能体。
需要对话可视件时，可声明 `conversation` 及对应 Vue 文件；它仍不会进入首页应用列表。
首页接口 `GET /api/v1/app/modules` 只返回有效启用的应用与混合模块；
`?surface=conversation` 返回有效启用且声明了对话组件的模块，包括技能组件。

技能模板的 `data.summary` 由校验器根据已保存的计划和任务完成状态生成。
没有对话卡片时，平台优先展示该已校验摘要；其他技能未提供摘要时显示查询完成提示。
失败的调用会显示“本次技能查询未完成，请确认模块启用状态和调用权限后重试。”；
同一回合部分成功、部分失败时，保留实际结果并附未完成提示。无论调用是否成功，
该模块查询回合都不会把模型的阶段产出写成新计划或画像更新，也不显示未落库的新任务引导。

模块目录中的文件职责如下；Vue 文件只在声明了对应入口时需要：

| 文件 | 职责 |
|---|---|
| manifest.json | 唯一编号、版本、负责人、平台接口版本、组件、布局和能力声明 |
| backend.py | `async load(context)` 返回数据；`validate(result)` 校验输出 |
| Card.vue | 首页卡片与可选对话展示 |
| Detail.vue | 可选详情；使用 action 事件请求平台操作 |
| fixtures.json | normal、empty、error 三种预览输入 |
| test_module.py | 模块业务测试；自动领取 module_definition fixture |

编号使用小写字母、数字、下划线，目录名必须一致。当前协议版本为字符串 `"1"`。
可公开的数据能力：`plan.read`、`achievements.read`；业务操作：`plan.task.set_done`。
需要新增能力时，先在主项目增加受控业务接口及验证，再扩展 SDK 白名单。
模块不得自行导入数据库或网络客户端。数据由 `await context.read("能力名")` 获取。
前端接收 `result`、`readonly`、`busy`；操作使用 `emit('action', 名称, 参数)`。
用户身份由服务器注入，参数不能包含 user_id 等身份字段。

输出形状为 `{ data, sources, empty }`，服务端验证后才送到组件。
模拟数据只用于明确标注的开发预览，不能作为正式接口失败时的替代结果。
新模块默认停用且没有授权。管理员在模块页选择允许的读取和操作能力后启用。
需要 AI 工具时，声明 `<模块编号>.read`，由管理员选择可调用的智能体；conversation 组件可选。
层级只影响归属和有效启停，子模块的数据、业务操作和智能体授权分别配置，不继承父级权限。
`effective_enabled` 要求自身及所有祖先都启用；`blocked_by` 只列出被停用的祖先，不含自身。
停用任一祖先后，即使子模块自己的开关仍打开，实际状态也会变为“受所属模块限制”，
后端拒绝其真实取数和工具调用；重新启用祖先后，仍按子模块自身及其他祖先的配置决定可用状态。
模拟预览仍可使用固定示例数据，便于开发者调试停用中的模块。

执行启动工作台命令可自动重建并载入本地新模块。开发预览查看的是工作台当前构建，
不是任意 Git 提交；候选提交的完整测试和安装版本显示在发布记录里。
前端、模块脚本与清单一起进入构建，不需要修改首页条件分支、登记 Python 子包或手写 API 类型。

## 3. 检查、预览与提交

在开发面板依次使用正常、空数据和读取失败场景，检查卡片与详情。
技能组件使用同一预览入口检查数据来源、JSON 返回和错误信息；无需制造卡片来调试工具。
模拟模式为只读。切换到“当前测试账号的真实数据”后，操作会更新当前隔离数据库中的账号数据。
确认修改任务后原有计划界面同步、刷新仍一致。

提交前在模板目录运行：

```powershell
python -m pytest -q
python -m ruff check .
python scripts/export_openapi.py --check
```

在前端目录运行 `npm ci`、`npm run build`、`npm run check:api`。
新增 API 时先执行导出脚本及 `npm run gen:api`，提交生成结果，不手改生成物。
`check:api` 用于干净提交，尚未提交的生成更新会被 Git 差异检查标出。

将模块提交到团队仓库，取完整的 40 位 Git SHA。在发布页填写 SHA，选择检查或部署并创建任务。
开发者只能申请；管理员确认后执行。反复确认同一任务不会创建额外部署。

## 4. 运行宿主机执行器

执行器只需 Python 标准库、Git 和 Docker。根目录执行：

```powershell
python deploy/module_executor.py --config .platform/executor.json
```

配置指定源码仓库、本地工作目录、固定 Compose 文件及两份私密环境文件。
执行器独立检出已提交代码；未提交内容不会被发布。执行器日志对环境配置中的凭据脱敏。
检出禁用本机换行符转换；检查源码以只读方式挂载并复制到容器内部运行，检查不会改写发布源码。
完整的脱敏命令日志存于执行器 state_directory 下的 logs，面板保存每阶段的日志摘要。
每次发布跑后端与模块测试、静态检查、契约检查、前端类型检查与构建。
镜像按提交号标记，测试环境为独立项目 `zhiyin-module-staging`，端口 5175/8015。
发布后验证健康、版本、登录、模块数据、原有计划接口和模块检查。

工作台配置在发布时复制到目标环境；管理页面的配置修改作用于当前环境。
在 5175 的管理页停用模块会立即阻止后端调用，首页及对话卡片在下次刷新或最多 15 秒后隐藏。
模块当前构建不存在、授权与候选清单不兼容时不能伪装为安装成功。

构建失败保持原环境；部署失败尝试恢复上一组镜像。第一次部署失败时停止应用容器，保留数据。
“恢复版本”只接受本机发布日志里曾经成功的提交号。回退的是应用代码，不撤销业务数据修改。
不要清空数据卷来处理发布故障。任务卡能区分构建失败、已恢复原版本与恢复失败。

## 5. 向服务器交付

交付确定提交的代码、镜像版本、Compose 文件及脱敏的环境变量清单。
佟在服务器创建独立环境与私密配置，执行同一初始化、构建和健康检查流程。
本首版不远程控制生产服务器。模块策略可以通过既有迁移工具导出；发布任务与租约不跨环境迁移。
保留数据库备份和本机执行记录用于审计。真实业务数据恢复须另行制定恢复方案。

## 6. 独立试接入验收

让另一位开发者只阅读本说明，用脚手架创建一个新模块，改名称和功能，完成模块测试、
模拟/真实预览、代码提交和测试部署。检查变更仅涉及其模块目录及必要的平台授权。
记录参与者、提交号、发现的问题和最终结果。自动模板复制测试不能替代真人独立试接入。

自动验收脚本：`deploy/accept_module_platform.py` 覆盖真实数据库、账号、重启与 Edge 浏览器；
`deploy/accept_module_conversation.py` 覆盖真实模型、模块卡片和历史记录；
容器内运行 `python scripts/module_runtime_acceptance.py --model` 验证 PostgreSQL 租约、串行发布、
权限撤销、真实模型函数调用及嵌入。脚本仅面向独立测试环境，不向当前 5173 数据库写入。

## v2：上传、自动验收与维护（当前流程）

### A. 从模板到一个可发布版本

1. 管理员先为团队成员配置 `developer` 角色。普通注册账号不能上传模块或管理项目。
2. 在工作台“开始开发”选择应用、技能或混合类型，填写模块编号、名称与负责人，下载模板 ZIP。
   同页查看平台能力及输入输出契约；编号必须与之后的项目编号相同。
3. 在“项目与版本”创建项目。项目负责人可添加已注册开发者账号，管理员可管理全部项目。
   `manifest.owner` 仅作展示，访问权限由项目成员记录决定。
4. 按模板本地开发并执行单元测试。`input_schema` 校验 `context.input`；`output_schema` 校验
   `ModuleResult.data`。`await context.read(...)` 读取当前用户的授权数据；禁止自行连数据库。
   以“开始开发”能力目录为当前清单，覆盖原第 2 节较早的数据能力列表。
5. 把**单个模块**打成 ZIP，然后上传。单模块平铺文件和仅含一个同名模块目录两种布局均可：

   ```text
   weekly_tasks.zip
   ├── manifest.json
   ├── backend.py
   ├── fixtures.json
   ├── test_module.py
   ├── dataflow.json       # 模板中的平台数据流验收声明
   ├── Card.vue            # 应用/混合模块需要
   └── Detail.vue          # 按声明选用
   ```

   PowerShell 打包示例，在项目根目录执行；只收集当前模板实际存在的文件：

   ```powershell
   $moduleFolder = 'zhiyin-src/template/zhiyin-modules/zhiyin_modules/weekly_tasks'
   $moduleFiles = Get-ChildItem -LiteralPath $moduleFolder -File | Where-Object { $_.Extension -in '.py', '.vue', '.json' }
   Compress-Archive -LiteralPath $moduleFiles.FullName -DestinationPath .platform/weekly_tasks.zip
   ```

   ZIP 最大 2 MiB，解压最多 8 MiB、100 个条目，单文件最多 1 MiB。不要打包整个项目、嵌套目录、
   `.env`、依赖目录、`conftest.py`、`__init__.py` 或安装脚本；文件名必须符合模块包规则。
6. 选择 `main` 或功能分支，例如 `feature-tao`。分支名为小写字母开头，后续可用小写字母、数字、
   下划线和连字符，最多 40 字符。已有分支须选其最新版本作为基线，平台基线使用状态栏提供的完整 SHA。
   如界面提示分支更新，先合并他人的修改，再重新选择基线提交。
7. 点击“上传并启动自动验收”。上传完成代表源码已保存；逐门禁显示的实际结果才是验收状态。
   同一项目的 `manifest.version` 不可覆盖，即使在不同分支也必须使用不同的版本号。

这套流程面向**内部可信团队**。管理员对项目配置一次运行信任，后续版本可自动执行。
未授权项目只保存源码及静态检查结果，在 `awaiting_trust` 等待；静态检查不构成恶意代码沙箱。
管理员同时启用“main 通过验收后自动部署”时，满足原授权及契约范围的 main 版本会自动进入发布队列。
feature 分支只自动验收，不自动发布；需要发布时使用已通过版本的发布按钮，后端仍检查授权和基线。

### B. 读懂检查、预览和失败结果

| 页面状态 | 含义与处理 |
|---|---|
| `awaiting_trust` | 管理员在项目设置中授权执行；普通成员不能修改信任策略 |
| `contracts` / `tests` / `build` / `dataflow` | 正在执行对应门禁，按具体错误、路径和事件修复；尚未收到结果不等于通过 |
| 验收失败 | 修源码后提高版本号重新上传；外部依赖暂时失败且源码未变，可重新验收原版本 |
| `configuration_required` | 权限扩展或契约变化需要平台与调用方一起升级，不能强制发布，处理方式见下一段 |
| 验收通过、未发布 | 查看项目自动策略或手动发起发布；执行器离线时先恢复执行器 |
| 发布失败 / 已恢复旧版本 | 版本详情允许重新验收，成功后按策略重新发布；不要反复点击原失败任务当作新部署 |
| 发布成功 | 测试环境版本接口、网关和发布记录已确认目标 SHA；模块是否可用另受授权与启停控制 |

`configuration_required` 没有“忽略检查”“强制通过”按钮。维护者需要在主项目中统一处理新增能力授权、
输入输出兼容和调用方依赖，走主项目测试与维护发布建立新的兼容基线；开发者随后从该基线提交一个新版本。
如不需要扩展，则恢复与现有基线兼容的声明和逻辑，再提高版本号上传。重验不会自动消除真实的契约变更。

版本详情的候选 JSON 来自该版本执行器报告，包含模拟和隔离真实数据结果。
只有候选 SHA 与测试环境实际运行 SHA 一致时，页面才给出“打开已运行此版本的测试环境”。
原“调试预览”页仍展示**工作台已构建版本**；它不会因上传新 ZIP 自动变成新版本组件。

**新模块安装后仍默认停用。** 管理员在测试环境 `/developer` 的“模块列表”选择所需读取、业务操作及
智能体权限并启用。父应用停用会阻止所属技能执行，子模块不继承父级权限。
工作台、测试环境、生产环境分别管理权限；v2 蓝绿发布不复制工作台策略覆盖目标环境策略。

### C. 编排一条完整数据流

在“数据编排”新建流程，添加模块节点，选择读取或已登记业务操作，并锁定模块版本。
“固定输入 JSON”提供常量；输入映射使用 JSON Pointer，例如 `$input/task_id` 或 `step_1/data/total`。
保存时检查重复编号、缺失引用、环路和接口版本；运行时再次校验输入与输出。

先用模拟模式运行，再用当前账号的隔离真实数据运行。真实写操作需显式勾选确认；当前支持多个只读节点和
至多一个末端业务操作。负责人或管理员发布编排修订，普通用户只运行已发布快照。
运行结果展示每个节点输入、输出、模块版本、失败位置及业务操作是否提交。中断且写入结果不确定时先核对回执，
不要用新的请求编号自动重复执行写操作。智能体注册的技能仍保持只读。

发布组件之前，执行器会用候选版本校验目标环境的全部已发布编排。固定旧版本的流程会明确阻止切流。
负责人或管理员先在该流程点击“暂停发布”；升级成功后点击节点的“使用当前安装版本”，保留原输入、绑定和操作，
检查并保存新修订，然后重新发布。普通用户在暂停期间不能启动流程；草稿、历史快照和已有回执保留。
保存草稿不会替换已发布的快照。发布切换期间若显示“平台正在更新”，稍后刷新再试；旧页面不能用旧构建继续发布。

### D. 维护者准备两个执行进程

`setup_module_platform.py` 仍负责工作台和私密环境文件，**不会自动完成 v2 源码工作器和蓝绿首次迁移**。
宿主机需安装 Python、Git、Docker/Compose；准备已提交、含本轮平台代码和验收脚本的受控源码仓库。
不要把未提交工作目录当作已验证基线，也不要覆盖正在使用的执行器配置。

下面是新配置示例，保存为私密的 `.platform/platform-v2.json`。所有路径使用本机绝对路径，
`source_base_commit` 必须换为真实存在的 40 位提交号；`repository` 是供执行器创建候选分支的独立克隆：

```json
{
  "repository": "E:/TZY/zhiyin-flash/.platform/platform-source",
  "state_directory": "E:/TZY/zhiyin-flash/.platform/platform-v2-state",
  "compose_file": "E:/TZY/zhiyin-flash/deploy/compose.platform.yml",
  "bluegreen_compose_file": "E:/TZY/zhiyin-flash/deploy/compose.bluegreen.yml",
  "workbench_env_file": "E:/TZY/zhiyin-flash/.platform/workbench.env",
  "staging_env_file": "E:/TZY/zhiyin-flash/.platform/staging.env",
  "workbench_url": "http://127.0.0.1:8014",
  "source_base_commit": "REPLACE_WITH_COMMITTED_40_CHARACTER_SHA",
  "worker_id": "source-tao-1",
  "browser_python": "E:/TZY/zhiyin-flash/.platform/browser-venv/Scripts/python.exe",
  "rollout_strategy": "blue_green",
  "bluegreen_shared_network": "zhiyin-module-staging_default",
  "bluegreen_drain_seconds": 190,
  "bluegreen_observation_seconds": 10
}
```

首次创建独立克隆可执行 `git clone --no-hardlinks --no-checkout . .platform/platform-source`。
受控仓库必须同时包含当前已安装版本及待迁移版本，并保留候选 `refs/heads/modules/` 分支。
若历史版本来自另一受控仓库，先取回经核对的提交历史；未知已安装 SHA 会阻断，不会自动使用旧基线。
私密环境文件及配置不进入 Git，两个环境的数据库、JWT 和 Redis 数据保持隔离。

浏览器门禁是每次候选验收的必需步骤。先在可信宿主机创建专用 Python 环境并安装 Playwright：

```powershell
python -m venv .platform/browser-venv
.platform/browser-venv/Scripts/python.exe -m pip install playwright
```

Windows 使用宿主机已经安装的 Microsoft Edge；Linux 的 Chromium 安装命令见服务器部署说明。
`browser_python` 指向上述环境的 **Python 绝对路径**，也可指向已验证安装了 Playwright 的现有专用环境。
该路径只由维护者配置，不从上传包读取。没有运行库或浏览器时验收失败，不跳过浏览器门禁。

固定脚本 `deploy/module_browser_gate.py` 在候选独立网页中真实登录，复用数据流验收的合成身份及
normal、empty、error 输入，逐一验证包括默认停用模块和纯技能在内的全部模块：卡片、详情、声明的对话组件、
JSON 结果、桌面与窄屏，以及 Vue 渲染错误。仅候选 Web 发布临时回环端口，API、数据库和 Redis 仍在内部网络；
候选页面的 CSP 将数据请求限定为自身地址，不访问已有工作台或 5173 数据。门禁不拦截 API、不伪造返回值，
也不调用模型。失败阻止发布，面板错误注明模块、场景及证据相对路径；完整报告和截图保存在
`state_directory/acceptance/jobs/任务编号/租约编号/`。成功数据流报告包含 `browser.passed` 与候选 revision。
源码验收规则版本为 `3`；规则 `2` 或缺少浏览器结果的旧报告不能直接发布，须重新验收。

完成下一节首次迁移之后，在两个独立终端启动：

```powershell
python deploy/module_source_worker.py --config .platform/platform-v2.json
```

```powershell
python deploy/module_executor.py --config .platform/platform-v2.json
```

Windows 也可在首次蓝绿迁移完成后，一次启动上述两个进程；保留上面的手动方式用于逐个排查：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/start_module_workers.ps1 -Config .platform/platform-v2.json
```

使用本机默认 `.platform/executor.json` 时可省略 `-Config`。脚本核对配置与已初始化的蓝绿路由日志，
以隐藏窗口启动两个宿主机进程；在 `state_directory/host-workers` 分别保存 PID、stdout 和 stderr。
重复运行会检查真实进程命令行中的 Python、仓库脚本与配置绝对路径后复用，不会自动停止任何 PID。
PID 被其他进程占用或启动失败时按提示检查具体日志。此命令**不是开机服务**，不创建计划任务；
宿主机重启后需再次运行，长期托管仍由服务管理器负责。

前者领取上传版本、生成候选、检查及发起符合策略的发布；后者领取发布任务并切流。
`--once` 只运行一轮，不作为常驻服务。新增并行源码工作器须使用不同 `worker_id`，保持同一个受控仓库和
部署状态目录；发布执行器维持单实例。正式托管请由宿主机服务管理器启动并保存 stdout/stderr。

工作台概览显示源码工作器心跳，不能据此推断发布进程一定在线；结合发布任务是否持续停在 `queued` 排查。
完整日志位于 `state_directory/logs`，蓝绿路由和镜像状态位于 `state_directory/bluegreen/deployment.json`。
不要手工修改其中版本或租约来跳过校验。

### E. 首次蓝绿迁移和日常恢复

首次迁移需要已有 `zhiyin-module-staging` 的数据库、Redis 网络及带 SHA 的原测试应用。
5175/8015 是稳定入口，蓝槽默认 5176/8016，绿槽默认 5177/8017；开始前检查端口占用。
当前 5173/8000 的项目不参与迁移。先暂停源码与发布执行进程，备份步骤见[服务器部署说明](模块服务器部署.md)。

待迁移 SHA 的两个镜像必须已构建，且包含 `ZHIYIN_RUN_BACKGROUND_WORKERS` 开关。
先在独立受控检出中构建，确认 `zhiyin-platform-api:SHA` 与 `zhiyin-platform-web:SHA` 存在。
`compose.bluegreen.yml` 为生成文件；需要更新时运行 `python deploy/module_bluegreen.py --write-compose`，不要手改。

```powershell
python deploy/module_bluegreen.py --config .platform/platform-v2.json prepare-migration --revision FULL_40_CHARACTER_SHA
python deploy/module_bluegreen.py --config .platform/platform-v2.json activate-migration
python deploy/module_bluegreen.py --config .platform/platform-v2.json status
```

`prepare-migration` 预热蓝槽，原入口继续服务；`activate-migration` 才交接原 5175/8015 端口。
首次交接具有短暂连接中断窗口，不将其算作后续正常蓝绿更新的连续访问验证。
迁移未完成或宿主机在交接期间中断时，确认执行进程已暂停，再执行：

```powershell
python deploy/module_bluegreen.py --config .platform/platform-v2.json recover-migration
```

这只恢复未完成的首次交接，保留数据库与 Redis。已经完成的蓝绿安装改用“发布记录”的“恢复已成功部署的版本”。
原历史 `replace` 模式仍保留，但 v2 常驻配置必须使用 `blue_green`，不能混跑两个发布执行器。
CLI `status` 也取得执行器锁，常驻发布进程运行时用工作台及下面的只读接口观察，不并行争抢锁：

```powershell
Invoke-RestMethod http://127.0.0.1:5175/__platform_route
Invoke-RestMethod http://127.0.0.1:5175/healthz
Invoke-RestMethod http://127.0.0.1:5175/version.json
```

三者应给出同一已安装版本。成功切流后旧槽至少排空 190 秒；不要为了下一次发布强行停止旧槽。
浏览器发现新版本会提示在新标签页打开，原页面及未提交输入保留。
镜像/路由回退不撤销业务数据，数据库迁移须兼容新旧应用短期共存。
