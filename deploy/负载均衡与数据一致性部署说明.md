# 职引 · 负载均衡与数据一致性部署说明

本文说明当前仓库 `docker-compose.perf.yml` 的部署方式、容器数量、请求分发、数据共享、并发写入、备份和回滚边界。

当前方案定位是：**一台服务器上的 Docker Compose 多 API 副本**。它能提升 HTTP 并发能力，并避免每个 API 副本重复运行后台任务；它不是跨服务器集群，也没有为 PostgreSQL、Redis、Nginx 做主从或故障转移。

## 一、部署结论

建议从下面的固定规模开始：

| 服务 | 数量 | 是否允许扩容 | 职责 |
| --- | ---: | --- | --- |
| `web` | 1 | 当前不扩 | Nginx 托管前端，并把 `/api/` 请求分发到 API 副本 |
| `zhiyin-flash` | 2 | 是 | 无状态 HTTP API；每个容器默认 1 个 Uvicorn 进程 |
| `zhiyin-background` | 1 | **禁止扩容** | 唯一的调度器和业务 Worker 进程 |
| `litellm` | 1 | 当前不扩 | 在 4 个 DeepSeek Key 之间按最少忙碌连接数分流 |
| `postgres` | 1 | 当前不扩 | 所有长期业务数据和向量数据的唯一事实来源 |
| `redis` | 1 | 当前不扩 | 共享读缓存、撤销标记加速和跨副本限流状态 |

启用四 Key 模型网关后，推荐部署一共是 **7 个容器**：

```text
1 个 web
2 个 zhiyin-flash API
1 个 zhiyin-background
1 个 litellm
1 个 postgres
1 个 redis
-------------------------
共 7 个容器
```

如果将 API 扩到 `N` 个，启用模型网关后的容器总数是 `N + 5`。不要把
`zhiyin-background` 一起扩容，否则定时任务和 Worker 可能重复执行；当前也不要扩容
`litellm`，它是本方案中统一管理供应商密钥的单例网关。

请求和数据流如下：

```text
浏览器
  │
  ▼
web / Nginx（5173 → 80）
  │  Docker DNS 解析服务名 zhiyin-flash
  ├───────────────┐
  ▼               ▼
API 副本 1       API 副本 2
  │               │
  ├──────┬────────┼───────────┐
  ▼      ▼        ▼           ▼
PostgreSQL       Redis      LiteLLM
                              │ least-busy
                              ├─ DeepSeek Key 1
                              ├─ DeepSeek Key 2
                              ├─ DeepSeek Key 3
                              └─ DeepSeek Key 4
  ▲
  │
后台单例 zhiyin-background

API 与后台单例还共同挂载：zhiyin-object-data → /app/data/objects
```

画像更新事件不依赖 API 进程内存，链路固定为：

```text
API 副本
  │  只写入 status=pending
  ▼
PostgreSQL / orc_event_outbox
  │  zhiyin-background 分批领取
  │  FOR UPDATE SKIP LOCKED + available_at 租约
  ▼
后台进程内的事件订阅者
  ▼
ImpactPropagationWorker
  ├─ 标记关联资产待重算
  └─ 失效基于旧画像生成的 AI 结果
```

处理成功后事件更新为 `published` 并填写 `published_at`；处理失败时保持
`pending`，延后 `available_at` 后重试。后台进程停止期间，新事件会保留在表中，
恢复后台后继续处理。

## 二、负载均衡设置在哪里

负载均衡由三部分共同完成，不是在某个“备用镜像”里单独完成的。

1. `docker-compose.perf.yml`
   - `zhiyin-flash` 不设置固定 `container_name`，也不占用宿主机 `8000` 端口，因此可以使用 `--scale` 创建多个副本。
   - 所有 API 副本使用同一个 `zhiyin-flash:<tag>` 镜像和同一套环境变量。
   - API 中设置 `ZHIYIN_RUN_IN_PROCESS_BACKGROUND=0`，防止每个副本各跑一套后台任务。
   - `zhiyin-background` 使用同一个后端镜像，但启动命令是 `python -m zhiyin_boot background`。

2. `zhiyin-src/template/zhiyin-web/nginx.conf`
   - Nginx 使用 Docker 内置 DNS `127.0.0.11` 解析 `zhiyin-flash`。
   - 扩容后的多个 API 容器共同注册在这个服务名下，Nginx 将请求发到解析出的容器地址。
   - 访问日志记录 `upstream_addr`、上游耗时和总耗时，可用于确认请求是否真正分散到多个副本。

3. 后端启动方式
   - API 只处理 HTTP 请求。
   - 调度器与业务 Worker 只在一个 `zhiyin-background` 容器内运行。
   - 每个 Python 进程有自己的 PostgreSQL 连接池，部署层必须限制池大小。

4. `docker-compose.litellm.yml`
   - 作为覆盖文件叠加到性能 Compose 或服务器现有的发布 Compose，不替换业务镜像。
   - 只在 Docker 内部网络暴露 `4000`，宿主机和公网均不发布该端口。
   - 两个 API 副本与后台容器都等待 LiteLLM 健康后启动，并通过
     `http://litellm:4000/v1` 调用模型。
   - 4 个供应商 Key 仅存在于 `deploy/litellm/.env.keys` 并注入 LiteLLM；业务容器
     只持有内部 `LITELLM_MASTER_KEY`，不能读取供应商 Key。

`zhiyin-flash` 与 `zhiyin-background` 是两个服务，但使用的是**同一个后端镜像**。镜像标签只是某次源码构建的版本标识，不是另一套独立源码。

### `R × W` 部署模型与启动方式

API 层的实际并发进程规模统一用 `R × W` 表示：

- `R`（Replica）：`zhiyin-flash` API 容器副本数，由 Compose 的 `--scale zhiyin-flash=R` 控制；
- `W`（Worker）：每个 API 容器内的 Uvicorn HTTP Worker 进程数，由 `ZHIYIN_WEB_WORKERS=W` 控制；
- API HTTP 进程总数是 `R × W`；
- 启用 LiteLLM 后整套部署的容器总数是 `R + 5`，不是 `R × W + 5`。`W`
  增加的是容器内部进程，不会创建新容器；另外 5 个容器是 `web`、
  `zhiyin-background`、`litellm`、`postgres` 和 `redis`。

例如 `R=3、W=2` 时：

```text
3 个 zhiyin-flash API 容器
× 每个容器 2 个 Uvicorn Worker
= 6 个 HTTP 进程

容器总数：3 + 5 = 8 个
```

推荐先使用 `R=2、W=1`，即 2 个 API 容器、每个容器 1 个 HTTP 进程。优先增加 `R`，便于隔离单个进程故障并观察 Nginx 是否把请求分散到不同容器；只有确认 CPU、内存和数据库连接预算足够后，再增加 `W`。

长期部署应把 `W` 写入服务器 `.env`：

```dotenv
ZHIYIN_WEB_WORKERS=1
```

然后通过 `--scale` 指定 `R`：

```powershell
$project = "zhiyin-dev"
docker compose -p $project -f docker-compose.perf.yml `
  up -d --scale zhiyin-flash=2
```

临时验证其他组合时，也可以在当前 PowerShell 会话中设置 `W`。例如启动 `R=3、W=2`：

```powershell
$project = "zhiyin-dev"
$env:ZHIYIN_WEB_WORKERS = "2"
docker compose -p $project -f docker-compose.perf.yml `
  up -d --scale zhiyin-flash=3
```

修改 `W` 后必须执行 `up -d` 让 API 容器按新启动命令重建；只执行 `restart` 不保证 Compose 用新环境值重建容器。启动后可检查容器数量和容器内进程：

```powershell
docker compose -p $project -f docker-compose.perf.yml ps
$apiIds = docker compose -p $project -f docker-compose.perf.yml ps -q zhiyin-flash
foreach ($apiId in $apiIds) {
  docker top $apiId
}
```

无论 `R` 和 `W` 取多少，`zhiyin-background` 都保持 1 个容器、1 个后台进程，不能跟随 API 一起扩容。数据库连接预算也必须按 `R × W × ZHIYIN_API_POOL_MAX_SIZE` 重新计算，具体公式见下一节。

### LiteLLM 四 Key 模型网关

LiteLLM 是独立的 OpenAI 兼容网关。业务容器仍发送
`model=deepseek-flash`，但目标地址改为 `http://litellm:4000/v1`；LiteLLM 再按
`least-busy` 从 4 个 deployment 中选择一个。当前网关保持单副本，不发布宿主机
端口，也不启用自动重试，避免压测失败被隐藏或产生重复计费。

供应商 Key 与业务配置必须分开保存：

- `deploy/litellm/.env.keys`：只给 LiteLLM 注入 4 个 DeepSeek Key；权限设为 `600`，
  不提交 Git；
- 根 `.env` 的 `ZHIYIN_LLM_API_KEY`：改为以 `sk-` 开头的内部 LiteLLM master key；
- 业务容器不能出现 `DEEPSEEK_API_KEY_1` 至 `DEEPSEEK_API_KEY_4`。

服务器以现有发布 Compose 为基础增加覆盖文件。以下示例使用当前服务器的
`docker-compose.r2w1-v2.yml`；直接使用仓库性能 Compose 时把该文件名替换为
`docker-compose.perf.yml`。

先备份配置并准备密钥文件：

```bash
cd /home/ubuntu/apps/zhiyin/release
stamp="$(date +%Y%m%d-%H%M%S)"
mkdir -p ../backups/litellm-$stamp
chmod 700 ../backups/litellm-$stamp
cp -p .env docker-compose.r2w1-v2.yml ../backups/litellm-$stamp/

cp deploy/litellm/provider-keys.example deploy/litellm/.env.keys
chmod 600 deploy/litellm/.env.keys
nano deploy/litellm/.env.keys
```

在 `.env.keys` 中填写 4 个 Key。不要把 Key 放进命令行、聊天记录或
`config.yaml`。另生成一个内部 master key，将它写入根 `.env` 的
`ZHIYIN_LLM_API_KEY`；生成命令本身不会把密钥写入 shell 历史：

```bash
python3 -c "import secrets; print('sk-' + secrets.token_hex(32))"
nano .env
```

先验证合并后的 Compose，并只启动网关：

```bash
sudo docker compose -p release \
  -f docker-compose.r2w1-v2.yml \
  -f docker-compose.litellm.yml \
  config --quiet

sudo docker compose -p release \
  -f docker-compose.r2w1-v2.yml \
  -f docker-compose.litellm.yml \
  up -d litellm

sudo docker compose -p release \
  -f docker-compose.r2w1-v2.yml \
  -f docker-compose.litellm.yml \
  ps litellm

sudo docker compose -p release \
  -f docker-compose.r2w1-v2.yml \
  -f docker-compose.litellm.yml \
  exec litellm python /app/verify_load_balancing.py
```

最后一条命令会并发发送 20 个最短模型请求并产生少量真实费用。它只输出 HTTP 状态
分布和匿名 deployment ID 计数；必须看到 20 个 HTTP 200 和 4 个不同 ID 才通过。

切换业务前，以仅当前用户可读的文件备份数据库路由，不要把结果打印到终端：

```bash
umask 077
sudo docker exec zhiyin-flash-postgres psql -U zhiyin -d zhiyin \
  -c "COPY (SELECT * FROM infra_ai_provider WHERE code='deepseek') TO STDOUT WITH CSV HEADER" \
  > ../backups/litellm-$stamp/infra_ai_provider_deepseek.csv
```

短维护窗口内停止入口、API 与后台，保留 PostgreSQL、Redis 和对象卷；然后把数据库
中的模型地址切到内部网关并重建服务：

```bash
sudo docker compose -p release \
  -f docker-compose.r2w1-v2.yml \
  -f docker-compose.litellm.yml \
  stop web zhiyin-flash zhiyin-background

sudo docker exec zhiyin-flash-postgres psql -U zhiyin -d zhiyin -c \
  "UPDATE infra_ai_provider SET base_url='http://litellm:4000/v1', api_key_env='ZHIYIN_LLM_API_KEY', updated_at=NOW() WHERE code='deepseek';"

sudo docker compose -p release \
  -f docker-compose.r2w1-v2.yml \
  -f docker-compose.litellm.yml \
  up -d --scale zhiyin-flash=2
```

确认业务调用成功后，删除数据库里遗留的供应商直连 Key；环境变量中的内部 master
key 仍然优先供业务容器调用 LiteLLM：

```bash
sudo docker exec zhiyin-flash-postgres psql -U zhiyin -d zhiyin -c \
  "UPDATE infra_ai_provider SET config=COALESCE(config, '{}'::jsonb)-'api_key', updated_at=NOW() WHERE code='deepseek';"
```

验收时应同时满足：LiteLLM healthy；业务日志不再出现直连
`https://api.deepseek.com/chat/completions`；LiteLLM 响应头中的
`x-litellm-model-id` 能观察到 4 个 deployment；业务容器环境中不存在
`DEEPSEEK_API_KEY_*`；宿主机没有发布 `4000` 端口。四 Key 若属于同一个 DeepSeek
账号，只提供分流与故障定位，不会扩大账号级并发额度。

## 三、部署前固定四件事

### 1. 固定 Compose 项目名

生产或开发服务器应长期使用同一个项目名，例如：

```powershell
$project = "zhiyin-dev"
```

后续每一条 Compose 命令都带上：

```powershell
docker compose -p $project -f docker-compose.perf.yml ...
```

项目名决定网络名和数据卷名。今天用 `zhiyin-dev`、明天改成 `release`，Docker 会创建另一组空卷，看起来就像“数据全部丢了”。这通常不是数据库被清空，而是启动到了另一组卷。

### 2. 后端和 Web 使用同一次提交构建

先确认部署提交：

```powershell
git status
git rev-parse HEAD
git log -1 --oneline
```

工作区必须干净。后端镜像和 Web/Nginx 镜像必须从同一个提交构建，标签建议只使用 ASCII 字符和 Git 短提交号，例如：

```text
ZHIYIN_IMAGE_TAG=dev-983ff5e
ZHIYIN_WEB_IMAGE_TAG=dev-983ff5e
```

将这两个值写进服务器 `.env`，不要只设置在一次性的终端变量里。否则以后执行 `docker compose up` 时可能回退到默认标签，悄悄启动旧镜像。

### 3. 固定副本数和连接池

推荐起始值写进 `.env`：

```dotenv
ZHIYIN_IMAGE_TAG=dev-<Git短提交号>
ZHIYIN_WEB_IMAGE_TAG=dev-<同一个Git短提交号>
ZHIYIN_WEB_WORKERS=1
ZHIYIN_API_POOL_MAX_SIZE=5
ZHIYIN_BACKGROUND_POOL_MAX_SIZE=2
```

连接池上限按 Python 进程计算：

```text
数据库连接预算约等于：
API 容器数 × 每容器 Uvicorn worker 数 × API 池上限
+ 后台进程数 × 后台池上限
+ 运维和迁移预留连接
```

推荐规模是：

```text
2 × 1 × 5 + 1 × 2 = 12 条应用连接上限
```

不要同时盲目增加 API 容器数和 `ZHIYIN_WEB_WORKERS`。两者都会增加 HTTP 进程数，也都会成倍增加数据库连接池。

### 4. 部署前备份

至少备份 PostgreSQL 和对象文件卷，并把备份复制到 Docker 主机之外。Docker 命名卷只是持久化位置，不等于备份。

严禁在保留数据的环境执行：

```text
docker compose down -v
docker volume rm ...
```

`-v` 会删除 PostgreSQL、Redis 和对象文件卷。普通的 `docker compose down` 不带 `-v`，数据卷会保留。

## 四、已有环境切换到多副本

如果服务器已经运行单实例，并且需要继续使用原有数据，必须使用原来的 Compose 项目名。先记录当前容器和数据卷：

```powershell
$project = "zhiyin-dev"
docker compose -p $project -f docker-compose.yml ps
docker volume ls
```

### 首次启用 outbox 消费前处理历史事件

本次上线只处理上线后产生的新事件，不重放旧版本遗留的 `pending`。这一步必须放在
短维护窗口内人工执行，代码不会在每次启动时自动跳过历史事件。

先停止入口、API 和旧后台进程，保留 PostgreSQL 与 Redis：

```powershell
docker compose -p $project -f docker-compose.perf.yml stop web zhiyin-flash zhiyin-background
```

统计并保存上线前的积压情况：

```powershell
New-Item -ItemType Directory -Force .\backup | Out-Null
docker exec zhiyin-flash-postgres psql -U zhiyin -d zhiyin -c `
  "SELECT event_type, COUNT(*) AS pending_count, MIN(created_at) AS oldest_created_at FROM orc_event_outbox WHERE status = 'pending' GROUP BY event_type ORDER BY event_type;" `
  | Tee-Object .\backup\outbox-pending-before-upgrade.txt
```

确认 API 和旧后台都已停止后，将这些旧事件保留为审计记录但标记为跳过：

```powershell
docker exec zhiyin-flash-postgres psql -U zhiyin -d zhiyin -c `
  "UPDATE orc_event_outbox SET status = 'skipped' WHERE status = 'pending';"
```

此操作不删除任何行。不要在 API 或后台仍可能写入新事件时执行，否则会把刚产生的新
事件一并跳过。

### 切换前必须单独导出旧对象文件

原 `docker-compose.yml` 只给后端挂载了只读迁移目录，**没有**把 `/app/data/objects` 挂到命名卷。因此旧单实例已经产生的上传文件或对象正文可能仍在 `zhiyin-flash` 容器的可写层里。直接重建该容器会丢失这些文件，即使 PostgreSQL 卷完好也无法找回正文。

先备份 PostgreSQL：

```powershell
New-Item -ItemType Directory -Force .\backup | Out-Null
docker exec zhiyin-flash-postgres sh -c `
  'pg_dump -U zhiyin -d zhiyin -Fc -f /tmp/zhiyin-before-perf.dump'
docker cp zhiyin-flash-postgres:/tmp/zhiyin-before-perf.dump `
  .\backup\zhiyin-before-perf.dump
```

再把旧容器里的对象文件复制到宿主机：

```powershell
New-Item -ItemType Directory -Force .\backup\objects | Out-Null
docker cp zhiyin-flash:/app/data/objects/. .\backup\objects
```

如果旧容器不是固定名称 `zhiyin-flash`，先用 `docker compose -p $project -f docker-compose.yml ps` 找到实际容器名。

然后校验、构建并启动：

```powershell
docker compose -p $project -f docker-compose.perf.yml config --quiet
docker compose -p $project -f docker-compose.perf.yml build
docker compose -p $project -f docker-compose.perf.yml up -d postgres redis
docker compose -p $project -f docker-compose.perf.yml up -d --scale zhiyin-flash=2
```

多副本全部启动后，把备份的对象文件恢复到共享卷。`zhiyin-background` 与所有 API 副本挂载的是同一个卷，所以复制到后台容器一次即可：

```powershell
$backgroundId = docker compose -p $project -f docker-compose.perf.yml `
  ps -q zhiyin-background
docker cp .\backup\objects\. "${backgroundId}:/app/data/objects"
docker exec -u 0 $backgroundId chown -R app:app /app/data/objects
```

恢复后应随机抽取已有文件，通过业务接口实际读取，不能只看目录中文件数量。

注意：

- `up` 会按新定义重建相关容器，但不会删除命名卷。
- 不要先执行 `down -v`。
- 如果此前使用了不同的项目名，应先查明旧 PostgreSQL 卷并完成备份或迁移，不能直接起一套空卷。
- 不要给 `zhiyin-background` 使用 `--scale`。

## 五、全新环境部署

全新环境先准备 `.env`，至少设置安全的 `ZHIYIN_AUTH_JWT_SECRET`、模型配置和不可变镜像标签。

### 1. 启动数据服务

```powershell
$project = "zhiyin-dev"
docker compose -p $project -f docker-compose.perf.yml config --quiet
docker compose -p $project -f docker-compose.perf.yml build
docker compose -p $project -f docker-compose.perf.yml up -d postgres redis
```

### 2. 如有迁移文件，导入策略和数据

当前 `docker-compose.perf.yml` 没有默认把 `deploy/` 挂到 `/migration`，因此一次性导入时需要显式挂载：

```powershell
docker compose -p $project -f docker-compose.perf.yml run --rm `
  -v ./deploy:/migration:ro `
  zhiyin-flash python scripts/migrate_db.py import `
  --dsn postgresql://zhiyin:zhiyin@postgres:5432/zhiyin `
  --in /migration/migration.json
```

导入完成后核对：

```powershell
docker compose -p $project -f docker-compose.perf.yml run --rm `
  -v ./deploy:/migration:ro `
  zhiyin-flash python scripts/migrate_db.py verify `
  --dsn postgresql://zhiyin:zhiyin@postgres:5432/zhiyin `
  --in /migration/migration.json
```

### 3. 启动完整服务

```powershell
docker compose -p $project -f docker-compose.perf.yml up -d --scale zhiyin-flash=2
```

## 六、不同类型的数据怎样在副本之间同步

这里的“同步”不是 API 容器之间互相复制。所有副本直接访问同一份共享数据源，因此不会存在“副本 1 一套数据库、副本 2 另一套数据库”的正常部署形态。

| 数据类型 | 唯一事实来源 | 多副本如何看到同一份数据 | 丢失后的影响 |
| --- | --- | --- | --- |
| 账号、密码凭据、登录会话 | PostgreSQL | 所有 API 和后台容器连接同一个 `postgres:5432` | 无备份时不可恢复 |
| 画像、任务、对话、笔记、课表、日历、报告、通知 | PostgreSQL | 所有写入和读取都走同一个数据库 | 无备份时不可恢复 |
| 向量及同步进度 | PostgreSQL + pgvector | 所有副本共享同一组向量表 | 可从源数据重建，但需要时间和嵌入服务 |
| 读缓存 | Redis | 所有 API 使用同一个 Redis 和键前缀 | 缓存可重建；丢失后首次读取变慢 |
| 限流令牌桶 | Redis | Lua 脚本在 Redis 内原子扣减，所有副本共用额度 | Redis 丢失后额度重置；故障期间限流会放行 |
| 登录撤销加速标记 | Redis，PostgreSQL 兜底 | Redis 快速判断，最终仍查 PostgreSQL 会话状态 | Redis 丢失不会恢复已撤销令牌，PostgreSQL 仍会拒绝 |
| 上传文件和对象正文 | `zhiyin-object-data` 命名卷 | API 和后台容器共同挂载 `/app/data/objects` | 卷丢失后，数据库可能还留着对象键，但文件无法读取 |
| 启动后装入内存的动态配置 | 每个 Python 进程各一份内存快照，源数据在 PostgreSQL | 启动时分别读取同一数据库 | 进程重启后重新读取；在线修改时需要重启全部副本以保持一致 |

### 动态配置更新的特别规则

多副本下，每个 API 进程都有自己的内存配置和 AI 路由快照。一次 HTTP 配置重载请求只会落到某一个 API 副本，不能保证其他副本同时刷新。

修改提示词、模型路由、功能开关或其他动态配置后，应统一重启全部 API 副本和后台单例：

```powershell
docker compose -p $project -f docker-compose.perf.yml restart zhiyin-flash zhiyin-background
```

重启后每个进程都会从同一个 PostgreSQL 重新装载。不要只调用一次配置重载接口就认为所有副本已经同步。

## 七、数据重叠和重复写入怎样处理

### 已有保护

1. **数据库主键和唯一约束**
   - 账号、凭据、资产版本等关键表依靠主键或唯一索引拒绝重复键。
   - 多处保存操作使用 `INSERT ... ON CONFLICT`，相同业务键再次写入时按定义更新或忽略。

2. **事务和行锁**
   - 需要多条 SQL 一起成功的写入使用 PostgreSQL 事务。
   - 任务会话状态更新使用 `FOR UPDATE`，避免两个请求同时读取旧状态后互相覆盖。

3. **资产版本号锁**
   - 同一用户、同一资产类型生成新版本时使用 PostgreSQL advisory transaction lock。
   - 锁内重新读取最新版本再生成下一版，避免两个 API 副本同时生成相同版本号。

4. **前端消息幂等键**
   - 对话请求携带 `client_msg_id`。
   - 已经完成过的消息重发时，服务会查询并返回上一次答复，减少断网重试和双击造成的重复模型调用。

5. **Nginx 不重试非幂等请求**
   - Nginx 只在连接错误、超时或部分网关错误时尝试另一个上游。
   - 配置没有启用 `non_idempotent`，因此不会主动把已经发送的 POST 请求复制到另一个 API 副本。

6. **后台任务单例化**
   - API 副本内不运行调度器和业务 Worker。
   - 只有一个 `zhiyin-background`，从部署层避免相同定时任务被多个副本同时轮询。

7. **画像事件跨进程投递**
   - API 只把完整 `DomainEvent` 信封写入 PostgreSQL `orc_event_outbox`，不调用发布进程内的订阅者。
   - `zhiyin-background` 使用 `FOR UPDATE SKIP LOCKED` 领取到期的 `pending` 事件，并用 `available_at` 作为租约。
   - 本地订阅回调成功返回后才确认 `published`；异常时保持 `pending` 并延迟重试。
   - 没有订阅者的事件直接确认，避免未知或已下线的事件类型永久积压。

### 当前仍存在的边界

以下情况不能宣称已经“绝对不会重复”：

- 对话幂等目前是“先查询、后处理、再记录”，`client_msg_id` 有普通索引，但没有数据库唯一约束。两个完全同时到达的相同请求仍可能都在记录生成前通过查询，从而重复调用模型并写入两份轮次。
- 后台任务依赖单例部署。如果运维误启动两个 `zhiyin-background`，当前调度查询没有用 `FOR UPDATE SKIP LOCKED` 抢占任务，可能重复触发。
- PostgreSQL outbox 提供跨进程的**至少一次**投递，不提供 exactly-once。消费者处理成功后、确认数据库状态前若进程退出，租约到期后事件可能再次投递，因此业务 Worker 仍须幂等。
- 本地对象存储对目标文件直接写入，没有数据库与文件系统之间的分布式事务。进程在“文件已写、数据库未写”或相反时退出，可能留下孤儿文件或无文件的对象记录。

因此，调用方仍应遵循：

- 每次用户动作生成稳定且唯一的请求幂等键，重试时复用原键，不能重新生成。
- 不要对未知结果的 POST 请求由客户端无限自动重试。
- 重要写接口要通过唯一业务键、事务或显式版本号补足数据库级保护。
- 定期检查对象键与实际文件是否一致，并清理确认无引用的孤儿文件。

## 八、数据丢失怎样处理

### 容器重建

完成性能部署并把旧对象迁入共享卷以后，普通容器重建不会丢数据，因为数据在命名卷中：

| 卷 | 内容 |
| --- | --- |
| `zhiyin-postgres-data` | PostgreSQL 全部数据库文件 |
| `zhiyin-redis-data` | Redis AOF 与缓存状态 |
| `zhiyin-object-data` | 上传文件和对象正文 |

前提是始终使用同一个 Compose 项目名，并且没有执行 `down -v` 或删除卷。

### 主机磁盘损坏

当前只有一个 PostgreSQL、一个 Redis 和一份本地对象卷。主机磁盘损坏时，命名卷也会一起丢失。因此必须建立主机外备份：

- PostgreSQL：定期 `pg_dump`，并把备份传到另一台机器或对象存储。
- 对象文件：定期归档 `zhiyin-object-data`，备份周期应与 PostgreSQL 接近。
- Redis：AOF 用于容器重启恢复，但核心数据仍以 PostgreSQL 为准；Redis 备份优先级低于 PostgreSQL 和对象文件。
- 至少做一次恢复演练。只有实际恢复成功的文件才算有效备份。

PostgreSQL 和对象卷应视为同一恢复点。只恢复数据库、不恢复对象文件，可能出现数据库记录存在但文件缺失；只恢复对象文件、不恢复数据库，则会留下无法被业务查到的孤儿文件。

### Redis 丢失

Redis 不是核心业务数据的唯一来源：

- 读缓存可以从 PostgreSQL 重建。
- 登录会话和撤销状态最终由 PostgreSQL 校验。
- 限流桶会归零，短时间内相当于重新开始计数。

Redis 故障时限流实现选择故障开放，因此服务可能继续处理请求，但保护模型和外部接口的限流会暂时变弱。运维告警不能因为“核心数据没丢”而忽略 Redis 故障。

## 九、对象文件的单机边界

`zhiyin-object-data` 是同一台 Docker 主机上的共享卷，适用于当前单机多容器部署。

如果以后把两个 API 副本分到两台服务器，本地 Docker 卷不再共享，不能照搬当前方案。必须先把对象存储替换为所有节点都可访问的存储，例如 S3 兼容对象存储、MinIO 或经过验证的共享文件系统。

跨主机之前还需要把 PostgreSQL、Redis、入口负载均衡和后台任务选主分别改造成外部共享服务；仅把 API 容器复制到第二台机器会造成文件不一致和服务发现失效。

## 十、部署后验证

### 1. 容器数量

```powershell
docker compose -p $project -f docker-compose.perf.yml ps
```

应看到：

- 2 个 `zhiyin-flash` 容器；
- 1 个 `zhiyin-background`；
- 1 个 `litellm`；
- 1 个 `web`；
- 1 个 `postgres`；
- 1 个 `redis`。

### 2. 健康检查

```powershell
docker compose -p $project -f docker-compose.perf.yml ps
docker compose -p $project -f docker-compose.perf.yml logs --tail=100 zhiyin-flash zhiyin-background web
```

API 副本应为 healthy，后台日志不应出现重复启动多套 Worker 的迹象。
启用模型网关时，`litellm` 也必须为 healthy，并确认业务容器不包含供应商 Key：

```bash
sudo docker compose -p release \
  -f docker-compose.r2w1-v2.yml \
  -f docker-compose.litellm.yml \
  ps

sudo docker inspect release-zhiyin-flash-1 \
  --format '{{range .Config.Env}}{{println .}}{{end}}' \
  | grep '^DEEPSEEK_API_KEY_' && echo '错误：供应商 Key 泄漏到业务容器'

sudo docker port release-litellm-1
```

最后一条命令应没有输出，表示 `4000` 没有发布到宿主机。

### 3. 确认请求分散

持续请求一段时间后查看 Nginx 日志：

```powershell
docker compose -p $project -f docker-compose.perf.yml logs --tail=300 web
```

统计日志中的 `upstream_addr=`。应看到至少两个不同的 API 容器 IP；如果长期只有一个地址，应检查实际副本数、Docker DNS 和 Nginx 镜像是否来自同一候选提交。

### 4. 确认共享数据

建议用同一个用户连续完成以下验证：

1. 登录并创建一条数据；
2. 连续刷新和读取，确保请求落到不同 API 副本时仍能看到同一结果；
3. 重启其中一个 API 容器，确认数据仍存在；
4. 重启 Redis，确认核心数据仍可从 PostgreSQL 读取；
5. 上传一个文件并从另一轮请求读取，确认共享对象卷有效；
6. 用同一个 `client_msg_id` 重放一次已完成请求，确认返回既有答复；
7. 不要在正式数据环境用并发重复请求做破坏性测试。

### 5. 确认画像事件被后台消费

先修改一个用户画像字段，再查询 outbox。新行应先出现为 `pending`，随后变为
`published`；关联资产应被标记待重算，基于旧画像的 AI 结果应失效。

查看各状态数量、待处理数量及最老事件年龄：

```powershell
docker exec zhiyin-flash-postgres psql -U zhiyin -d zhiyin -c `
  "SELECT status, COUNT(*) FROM orc_event_outbox GROUP BY status ORDER BY status;"

docker exec zhiyin-flash-postgres psql -U zhiyin -d zhiyin -c `
  "SELECT event_type, COUNT(*) AS pending_count, MIN(created_at) AS oldest_created_at, NOW() - MIN(created_at) AS oldest_age, MIN(available_at) AS next_available_at FROM orc_event_outbox WHERE status = 'pending' GROUP BY event_type ORDER BY oldest_created_at;"
```

若 `pending_count` 持续增长或 `oldest_age` 持续变大：

1. 确认只有一个 `zhiyin-background` 且容器处于运行状态；
2. 查看后台日志中的 `outbox 事件投递失败` 或 `PostgreSQL outbox 轮询失败`；
3. 对比 `available_at`，失败事件会在延迟后再次可领取；
4. 修复订阅处理异常后等待自动重试，不要直接把问题事件手工改为 `published`。

可用下面的验收方式验证停机恢复：停止 `zhiyin-background`，修改一次画像，确认事件
保持 `pending`；重新启动后台后，确认同一行最终变为 `published`。

## 十一、回滚

当前负载均衡改动没有要求把 PostgreSQL 拆成多库。需要回到单实例时，保留现有数据卷即可。

先停止性能部署，**不要带 `-v`**：

```powershell
docker compose -p $project -f docker-compose.perf.yml down
```

然后使用确认过的旧镜像或旧提交启动基础部署：

```powershell
docker compose -p $project -f docker-compose.yml up -d
```

必须保证 `zhiyin-background` 已停止，因为基础部署的单个 `zhiyin-flash` 默认会在进程内恢复运行调度器和 Worker。若两个同时存在，后台任务会重复。

回滚前后都应核对：

- 使用的是同一个 Compose 项目名；
- PostgreSQL 卷没有变化；
- 没有执行 `down -v`；
- 镜像标签对应已登记的 Git 提交；
- 登录、画像、会话、报告和对象文件仍可读取。

若只回滚 LiteLLM，不回滚 API 多副本，则在维护窗口内执行：

1. 停止 `web`、`zhiyin-flash` 和 `zhiyin-background`；
2. 恢复备份的根 `.env`，把数据库 `deepseek.base_url` 改回
   `https://api.deepseek.com`；
3. 使用原发布 Compose、不带 `docker-compose.litellm.yml` 重建业务服务；
4. 显式停止并删除 LiteLLM 容器，但不要执行 `down -v`；
5. 验证业务日志重新出现 DeepSeek 直连成功记录。

## 十二、当前方案能保证什么、不能保证什么

当前方案能做到：

- 两个 API 副本共享同一套长期数据；
- HTTP 请求经过 Nginx 分发；
- API 扩容时后台任务仍保持单例；
- 画像更新事件可从 API 副本经 PostgreSQL outbox 投递到独立后台进程；
- 缓存和限流状态在 API 副本之间共享；
- 关键资产版本与部分状态更新有事务和数据库锁保护；
- 容器重建时命名卷数据保留。

当前方案不能做到：

- PostgreSQL、Redis、Nginx 或宿主机故障后的自动切换；
- 跨服务器共享本地对象卷；
- 所有业务请求的全局 exactly-once；
- 数据库与对象文件的原子提交；
- 一次配置热加载自动广播到所有 Python 进程；
- 在没有外部备份的情况下抵抗主机磁盘损坏或误删数据卷。

如果目标从“单机压测和扩容”升级为“生产高可用”，下一阶段至少需要：外部 PostgreSQL 高可用与备份、Redis 高可用、S3 兼容对象存储、两个以上入口实例、后台任务选主或队列消费锁，以及数据库级幂等约束。
